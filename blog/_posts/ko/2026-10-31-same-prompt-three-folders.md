같은 요청으로 시작한 세 작업 공간에서 서로 다른 설계 질문이 나왔다. 내가 비교할 기준은 문서의 상세도가 아니라 한 신청이 만들어 내는 모델 호출 수였다. 호출 단위를 명세에서 따져 보니 구현 전에 바꿀 부분이 드러났다.

## 작업 목표

목표는 그대로였습니다. 과제를 이해하고, 실제 Azure에서 돌아가는 데모를 만드는 것. 달라진 건 시작한 곳의 개수였습니다.

먼저 오전 10시 3분, 새 폴더에 첫 커밋이 생기고 brainstorming 요청이 들어갑니다. 이걸 시도 3이라고 부르겠습니다. 시도 4는 10시 18~19분에 같은 방식으로 시작했고, 세 번째 폴더는 오후 1시 6~7분에 시작했습니다. 이 블로그에서는 이 세 번째 폴더를 이제부터 본선이라고 부릅니다.

왜 폴더를 세 개나 열었는지, 왜 세 번째가 본선이 되었는지는 기록에 없습니다. 그래서 추측하지 않겠습니다. 대신 기록으로 할 수 있는 게 하나 있습니다. 세 곳에 같은 문장이 들어갔으니, 비교가 됩니다.

자정까지 세 폴더에 쌓인 커밋은 86개였습니다. 시도 3에 26개, 시도 4에 4개, 본선에 56개. 그날 기록에 남은 tool 실패도 37건입니다.

## 요청 범위와 수행 절차

요청은 이랬습니다.

> "/superpowers:brainstorming [과제 파일] …capstone 프로젝트 과제입니다. 해당 요구사항을 실제 Azure 에서 데모 구현을 해야 합니다. 과제 내용을 파악하고 핵심 요구사항을 정리해주세요"

시도 4에 넣은 것만 끝에 "상세하게"(오타로 "상게하게")가 붙어 있었고, 나머지는 같은 문장입니다. 그런데 돌아온 답은 같지 않았습니다.

**시도 3**은 요약을 쓴 다음, 과제 파일 두 개를 읽는 일을 리서치 서브에이전트에게 넘기고 결과를 보고서로 저장했습니다. 저는 별도의 데모 설계 문서를 붙여서 이것도 반영해 달라고 했고, 이렇게 덧붙였습니다. "데모를 구성하는 부분이라 일정 부분은 가정을 넣을거라 너무 법적인 부분은 고민하지 않아도 되요". 그 뒤로 범위·시나리오·서비스를 두고 승인 양식이 길게 오갔고, 11시 47분에 제가 "지금은 문서 검토까지만 진행"을 고르면서 멈췄습니다.

**시도 4**는 1분 남짓 동안 선택지 질문 네 개를 던졌습니다. 데모를 어디까지 깊게 할지, 어느 나라를 가정할지, 에이전트 스택은 무엇으로 할지, 시간은 얼마나 있는지. 그다음 설계를 네 부분으로 나눠 보여 줬고, 제 답은 "네" 여섯 번이었습니다. spec은 10시 29분에, 19개 Task짜리 구현 계획은 11시 17분에 커밋됐습니다. 11시 37분에는 진짜 질문을 하나 했습니다.

> "'리전은 koreacentral 하나만 사용하고 Azure Policy "Allowed locations"로 강제한다.' 라고 되어있는데 그러면 Microsoft Foundry 모델의 Global standard 배포는 허용되나요?"

에이전트는 허용된다고, 그 정책만으로는 막을 수 없다고 답하면서 거주 요건 관점에서는 위반이라고 했습니다. 그리고 지역 밖 모델 SKU를 거부하는 커스텀 정책을 계획에 추가했습니다.

**본선**은 질문이 여섯 개였습니다. 이 저장소를 어디에 쓸지, 나라, 일정, 스택, 심사역 화면을 어느 수준으로 만들지, 비용과 보안 수준. 오케스트레이션 접근안 중 하나를 고르게 한 뒤, 설계를 다섯 부분으로 나눠 부분마다 승인을 받았습니다. 저는 두 번 의견을 냈습니다. 1부에서는 "Underwriting 과 Early-warning 에서는 LLM 을 좀 더 강화해주세요", 3부에서는 "Model 은 한국 내 Regional 배포 모델만 사용이 어려워서 Global Standard 모델로 해야 합니다."

그러니까 같은 날 같은 주제에 반대되는 답이 두 개 있습니다. 시도 4의 계획은 11시 43분에 Global Standard를 막았고, 1시 33분에 저는 본선에 Global Standard로 가야 한다고 했습니다. 어떻게 생각이 옮겨 갔는지는 기록에 나오지 않습니다.

## 관찰된 문제

**먼저, 같은 요청을 두 번 넣었을 때.** 1시 3분에 시도 4에 brainstorming 요청을 다시 붙여 넣었습니다. 에이전트는 처음부터 다시 하지 않았습니다. "이 과제는 이미 설계서(…)와 구현 계획서(…)까지 끝났습니다. 다시 처음부터 brainstorming을 하지 않고, 요청하신 핵심 요구사항만 원문 기준으로 다시 정리합니다." 4분 뒤 같은 문장이 새 폴더로 들어갔고, 그날 시도 4의 기록은 이 답에서 끝납니다. 여기서 본 건 이겁니다. 에이전트는 폴더에 남은 이력을 읽기 때문에, 오래된 폴더에서의 "새 출발"은 새 출발이 아닙니다.

**다음으로, 승인하지 않은 spec.** 1시 58분에 본선이 한국어 spec을 커밋하고 승인을 물었습니다. 저는 승인하지 않았고, 뭘 바꿀지 묻자 3.2절을 그대로 옮겨 붙였습니다. 은행 거래 적요나 가맹점명 같은 한국어 텍스트를 매출·대표자 개인 이체·타 금융사 상환·세금·급여 등으로 분류하고, "대량 처리는 mini급 모델이 맡습니다"라는 대목이었죠. 그리고 물었습니다.

> "그럼 모든 은행 트랜잭션당 LLM 호출이 1번 발생되어야 하는거 아닌가요?"

**그다음은 첫 실제 Azure 비용.** 인프라 계획의 마지막 T10이 실제 배포였습니다. 에이전트가 Service Bus Premium만 월 약 $677이라고 짚었고, 저는 "문서만"을 골랐습니다. 그러고는 "실제 배포 이후의 다음단계가 있나요?"라고 물었고, 1분 뒤 "배포 진행"이라고 썼습니다. 그 1분 사이에 왜 마음이 바뀌었는지는 기록에 없습니다. 배포는 세 군데에서 걸렸습니다. 모델 배포 이름에 예약어가 들어 있었고, Private Endpoint가 그게 기대는 모델 배포보다 먼저 만들어졌고, smoke 점검의 예전 Assistants API 호출이 새 Foundry 프로젝트에서 실패했습니다. 거기에 테넌트 정책이 Key Vault·Cosmos DB·Storage의 공용 접근을 강제로 끄고 있었습니다.

**시도 3의 리뷰는 계속 뭔가를 찾아냈습니다.** 저녁에 시도 3은 계획을 Task 단위로 돌렸습니다. Task 9개를 하나씩 새 구현 서브에이전트에게 맡기고, 끝나면 독립 리뷰어에게 넘기는 방식이었는데요, 9개 중 7개가 첫 리뷰에서 "NEEDS_FIXES"를 받았습니다. 예를 들면 현금 버퍼가 정확히 30일인데도 30일 기준 *미달*로 판정됐습니다. 반올림된 Decimal 나눗셈 때문에 29.999…가 된 거였습니다.

## 대응과 결과

**spec은 질문 하나로 충분했습니다.** 에이전트가 계층형 분류를 제안했습니다. 규칙 → 중복 제거 → 배치 LLM → 캐시. 저는 "이런 부분에서는 Microsoft-Decision-1 모델같은게 좋은 옵션이 될거 같습니다. (비용은 저렴하고 빠른 모델)"이라고 보탰고, 고친 spec은 규칙 → 중복 제거 → Microsoft-Decision-1 → mini LLM 폴백 → 캐시가 됐습니다. 평가 지표로 호출 수, 규칙 처리 비율, 캐시 적중률, 임계값별 정확도가 붙었고, 한국어 분류 품질과 Korea Central 배포 가능 여부는 아직 검증 전이라는 위험도 적혔습니다. 2시 7분에 승인했습니다. 아마 그 질문 하나가 그날 제가 쓴 것 중 꽤 쓸모 있는 축이었던 것 같습니다.

**조사는 에이전트가 갈래를 나눠 했습니다.** 로컬 도메인 코어인 P1이 병합되고 제가 "진행해주세요"라고 하자, 에이전트는 인프라 조사를 다섯 갈래로 나눠 동시에 돌렸습니다. private Foundry agent 구성, Korea Central 모델 가용성, Container Apps 네트워킹, Durable Functions, Content Safety와 가격. 몇 분 뒤 Data Zone 갈래도 하나 더 보탰고요. 결과를 기다리는 동안에는 가만히 있지 않고 저에게 결정 두 가지를 먼저 물었습니다. 조사에서는 2026년 7월 9일에 GA된 아시아·태평양 Data Zone이 나왔는데, 우리 spec에 적힌 문장과 어긋나는 내용이었습니다. 에이전트는 기본값을 그쪽으로 바꾸자고 제안했고, 저는 "global"로 답했습니다. 이어서 제가 골랐던 네트워크 안대로면 오케스트레이터가 내부 서비스를 부를 수 없다는 걸 찾아내 Container Apps 환경을 두 개로 나누자고 했고, 저는 동의했습니다.

**비용 승인은 따로따로 받았습니다.** 인프라 계획은 "T10 전에 멈춤"으로 승인했고, T10 차례에는 "문서만"을 골랐고, 그다음에야 배포하라고 했습니다. 배포에서 걸린 세 가지는 에이전트가 고쳤고, 테넌트 정책은 우회하지 않고 README에 적어 뒀습니다. 프로비저닝은 7.6분 걸렸고 VNet 안 smoke 점검 21개가 모두 통과했습니다. 이제 하루 약 $22씩 나가는 Service Bus Premium을 어떻게 할지 묻길래 pause를 골랐습니다.

**시도 3에서는 리뷰 루프가 제 몫을 했습니다.** 수정은 매번 그 수정만 보는 리뷰어에게 다시 갔고, 수정 라운드는 최대 5회까지였습니다. 구현 서브에이전트가 추측하지 않고 "NEEDS_CONTEXT"로 멈춘 게 세 번이었는데, 그중 하나는 제게 질문으로 돌아왔습니다. 동의가 만료된 뒤 고객이 다시 동의하면 어떻게 할지. 저는 권장안을 골랐습니다. 밤 11시 56분, 마지막 Task는 두 번째 수정 라운드에 들어가 있었습니다. 본선은 방식이 달랐습니다. 에이전트가 P1을 "Native"로, 그러니까 자기가 직접 구현하고 브랜치 전체를 한 번 리뷰받는 방식으로 하자고 추천했습니다. 계획된 테스트는 95개였고, 리뷰 판정 "with fixes"와 수정 두 건을 거친 뒤 100개가 통과해 2시 56분에 병합까지 갔습니다.

폴더끼리 완전히 떨어져 있던 것도 아닙니다. 오후 4시 33분, 시도 3에 이렇게 요청했습니다. "기존 spec 에 다가 … 를 활용해서 업데이트 해주세요. … 특히 3 에이전트 설계 부분이 맘에 들어요." 가리킨 문서는 본선의 spec이었습니다. 그 파일이 시도 3 폴더 안에는 없었기 때문에, 에이전트는 짐작하지 않고 전체 경로를 알려 달라고 되물었습니다.

밤 9시 20분, 본선의 실제 Azure smoke는 24/24 통과했고, 신청 1건이 52초 만에 approved까지 갔습니다.

돌아보면, 같은 요청이 같은 프로젝트를 세 번 만들어 주지는 않았습니다. 질문이 달랐고, 제 답이 달랐고, 폴더에 남은 이력도 영향을 줬습니다. 아마 본선을 앞으로 밀어 준 건 요청 문장이 아니었을 겁니다. 에이전트가 쓴 걸 읽고, 거기에 평범한 질문을 하나 던진 것이었습니다.

## 오늘의 교훈

spec은 승인하기 전에 읽자. "이거 모델 호출이 몇 번 생기죠?" 같은 평범한 질문 하나가 나중의 재설계보다 훨씬 싸다.
