로그인 오류가 났던 환경에서 작업을 재개했다. 이전 오류를 다시 고치기 전에 현재 인증 상태부터 확인했다. 그제야 모델을 배포할 용량과 Spark 의존성이 다음 단계를 막고 있다는 사실을 구분할 수 있었다.

## 작업 목표

사실 첫날이라고 부르기도 애매합니다. 시도 1 저장소에는 전날 이미 첫 커밋들(사례 문서, 한글 번역, 과제 설명 문서)이 올라가 있었거든요. 10/26 커밋 기록을 보면, 제가 가진 대화 기록이 시작되기 전에도 하루치 작업이 꽤 있었습니다. 오전에 요구사항 분석과 데이터베이스 설계, 오후에 "two-agent MVP" spec과 plan, 그리고 저녁 6시 무렵까지 기능 커밋 여섯 개. 고정 테스트 데이터와 mock API, Fabric SQL에 workflow 저장, Foundry·Fabric client, notebook 계산, 가드를 건 에이전트 두 개, 발표용 wizard까지요.

그런데 거기서 멈췄습니다. 기억에 남은 건 Azure login 오류 하나였습니다. plan 기준으로 Task 1–6은 끝났고, Task 7–9(인프라, Fabric 초기화, 실제 클라우드 시연)는 남아 있었습니다.

그래서 저녁 6시 45분의 목표는 단순했습니다. 막힌 걸 풀고, MVP를 실제 Azure에서 끝까지 돌려 보는 것.

## 요청 범위와 수행 절차

먼저, 시작은 좀 게을렀습니다. 이전 세션에서 GitHub 동기화를 기록해 둔 파일 하나만 붙이고 아무 말도 쓰지 않았거든요. 그런데 에이전트가 짐작으로 움직이지 않았습니다. 이 파일로 뭘 하고 싶은지 선택지를 주며 되물었고, 저는 "이전 작업을 이어서 진행"을 골랐습니다. 그러자 이 PC도 `main`으로 바꾸고 로컬과 원격이 같은 커밋인지 확인하더군요. 아마 그 전 작업은 다른 PC에서 했던 것 같습니다. 이 PC를 맞추는 게 첫 일이었으니까요.

다음으로 진짜 질문을 했습니다.

> "mvp 구축을 진행중이였는데 azure login 에서 이슈가 나서 진행이 안되었는데 그 상태를 확인해줄래요?"

오류 메시지는 붙이지 않았습니다. 아마 오류 원문이 이미 없었던 것 같습니다. 돌아온 답은 표 하나였는데, 그날 상황에 대한 제 생각이 꽤 바뀌었습니다.

- Azure CLI login은 정상. Graph·Foundry·Fabric·OneLake·SQL token 발급도 모두 성공했고, 실제 API 호출도 됨.
- MVP는 login 단계가 아니라 인프라 사전 점검(preflight) 전에 멈춰 있음.
- 아직 앱이 쓰는 환경변수도, `.env` 파일도 없음.
- 저장된 기록에는 모델 목록 조회가 120초 동안 응답이 없어 중단됐다고 되어 있고, 당시 `az login` 오류 원문은 남아 있지 않아 "원인은 확정할 수 없다".

마지막 줄이 마음에 들었습니다. 그럴듯한 원인을 지어낼 수도 있었을 텐데, 기록에 있는 것과 없는 것을 나눠서 말해 줬으니까요. (10분 뒤 추가 확인을 마치고는 이전 중단이 로그인 서버 연결 실패였다고 했습니다. 어느 쪽이든 이제 걸림돌은 아니었습니다.)

그럼 제 답은요? "진행" 한 단어였습니다.

그날 저녁 제 쪽 대화는 대부분 이 단어였습니다. 그날 제가 직접 쓴 메시지 중 여섯 개가 "진행", "계속 진행", "승인"이었어요. 실제 결정은 다른 곳에서 일어났습니다. 돈이 들거나 제 PC를 바꾸는 일 앞에서는 에이전트가 멈추고 선택지가 달린 질문(승인 양식)을 띄웠고, 저는 대개 그중 하나를 고르는 식으로 답했습니다.

## 관찰된 문제

**먼저, 고른 모델에 자리가 없었습니다.** "모델은 gpt-6.1-sol 로 해주세요"라고 했더니, 에이전트가 Korea Central 할당량을 확인하고 문제를 들고 왔습니다. 그 모델의 GlobalStandard는 이미 사용량이 한도를 넘었고, 신규 용량은 0이라는 것. 다른 배포 유형으로 가거나 GlobalStandard를 유지하고 할당량 증액을 알아보는 두 길을 내밀었고, 저는 유지를 골랐습니다. 에이전트는 그 선택을 설계에 반영하면서, 기존 할당은 다른 리전에 있고 그걸 옮겨 쓸 수 있다고 *가정하지 않았다*고 분명히 적었습니다. 그리고 할당량 증액 요청 양식을 안내했죠. 맞는 말이었지만, 저는 막혀 버렸습니다.

**다음으로, 첫 실제 클라우드 실행에서 아무도 계획하지 않은 일이 터졌습니다.** 유료 배포를 승인하자 Foundry project와 모델, Fabric F2, Workspace, Lakehouse 세 개가 생성됐습니다. Notebook 하나도 생성됐는데, 비동기 응답이 지역 주소를 돌려주는 바람에 에이전트의 로컬 상태 기록이 중간에 끊겼습니다. 그다음 end-to-end smoke test는 Spark까지 가서 멈췄습니다. Fabric runtime이 앱이 고정한 것과 다른 Pydantic 버전을 미리 로드해 두었고, 앱의 안전 검사가 실행을 막은 거였습니다.

**자잘한 헛발질도 많았습니다.** 그날 기록에는 tool 실패가 14건 남아 있습니다. view 범위 초과, 파일과 맞지 않는 patch, 없는 경로, GitHub tool의 504, 404가 난 문서 페이지까지요. 거의 다 에이전트가 알아서 넘어갔고, 저는 아마 그때 대부분 몰랐던 것 같습니다.

## 대응과 결과

**용량 문제는 질문을 바꿔서 넘었습니다.** 할당량 증액을 기다리는 대신 "gpt 6 다른 모델은?"이라고 물었습니다. 에이전트가 리전을 조회해 짧은 표를 돌려줬는데, 다른 GPT-6 모델 세 개는 200,000~250,000 TPM이 비어 있고 제가 원한 모델만 0이었습니다. gpt-6-sol을 추천하면서 가격과 tool 호출 호환성은 더 확인해야 한다고 덧붙였고요. "gpt-6-sol 로 해줘"라고 하자 2분 만에 설계와 plan이 바뀌었습니다. 이때까지 배포한 건 아무것도 없었습니다.

**비용은 승인을 단계별로 받게 두었습니다.** 의외였던 건, 에이전트가 "계획 쓰기"와 "돈 쓰기"를 얼마나 꼼꼼히 나누는가였습니다. 순서는 이랬습니다.

1. 리소스 목록: 전용 resource group, Foundry 계정과 project, gpt-6-sol 50,000 TPM 배포, Fabric F2, 그리고 그 안에 초기화할 항목들. F2는 시간당 약 $0.42, 모델은 백만 토큰당 가격까지 적고, 이 승인은 배포 승인이 *아니라고* 못 박았습니다.
2. 상세 계획: F2를 4시간 시연에 쓰면 약 $1.68, 한 달 내내 켜 두면 약 $306.60. 저는 Bicep 생성과 로컬 검증까지만 승인했습니다.
3. Bicep 컴파일 성공, `what-if` 결과 신규 6개·기존 리소스 변경 없음, Checkov는 통과 2개와 경고 1개. 경고는 제가 이미 받아들인 공개 개발용 endpoint 예외였고, 숨기지 않았다고 따로 밝혔습니다.
4. 제 Windows PC에 ODBC Driver 18을 설치하는 일도 공유 시스템을 바꾸는 일이라 따로 물었습니다.
5. 그다음에야 유료 배포. 저는 "승인" 한 단어로 답했습니다.

**잃어버린 Notebook은 복구 전에 물어봤습니다.** 새로 만드는 대신, 이미 생성된 Notebook의 ID(`<notebook-id>`)를 소유 표시와 코드 일치를 확인한 뒤 복구 기록에 연결하겠다고 제안했습니다. F2가 지금 켜져 있어 비용이 나가고 있다는 것도 다시 알려 줬고요. 승인했습니다.

**이제 Spark 문제입니다. 범위가 좁은 해결책을 가격표와 함께 가져왔습니다.** 기존 Workspace 안에 전용 Fabric Environment 하나를 두고, 고정 의존성을 게시해 두 Notebook에 연결하되 Notebook 코드는 그대로 두는 안이었습니다. 승인했고, 밤 10시 39분에 정상 경로가 처음부터 끝까지 통과했습니다. Foundry → OneLake → 정규화·심사 Notebook → SQL.

하루는 리뷰로 끝났습니다. 아마 에이전트가 브랜치 전체를 새 리뷰어 에이전트에게 넘긴 것 같습니다. 기록에 제가 쓴 적 없는 영어 지시문이 읽기 전용 리뷰를 요청하고 있거든요. 결과는 Critical 없음, Important 두 개였고 둘 다 재시작 이야기였습니다. lease가 아직 살아 있는 workflow를 재시작이 영영 놓쳐 버릴 수 있다는 것, 그리고 결과를 모르는 제출을 자동으로 넘겨받을 수 있다는 것. 그날 마지막 커밋(밤 11시 41분)의 제목은 "fix: recover stopped workflows without repeating unknown submissions"입니다. 아마 이 지적에 대한 답이었을 겁니다.

돌아보면, 저는 login 오류와 씨름할 각오로 들어왔는데 그 씨름은 끝내 일어나지 않았습니다. 시간을 아껴 준 건 제가 기억으로 과거를 설명하기 전에 에이전트가 지금 상태부터 확인하게 둔 것이었고, 마음을 편하게 해 준 건 돈이 드는 결정이 매번 분명한 질문으로 제게 돌아왔다는 점이었습니다. 처음 해 보는 분이라면, 첫 메시지를 완벽하게 쓰려고 애쓸 필요는 없습니다. 지금 상태를 물어보기만 하면 됩니다.

지난 일을 길게 다시 설명하기보다 "지금 상태부터 확인해 줘"로 시작하자. 그리고 돈이 드는 결정은 끝까지 내가 내린다.
