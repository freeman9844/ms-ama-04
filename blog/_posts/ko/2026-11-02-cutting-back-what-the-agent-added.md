안녕하세요. 지난 글에서는 데모를 막던 보안 통제 하나를 꺼 두는 이야기를 했는데요, 이날은 비슷한 일이 다른 모양으로 돌아왔습니다. 에이전트가 쌓아 올린 것을, 때로는 승인한 지 한 시간도 안 돼서 다시 덜어내는 일이었습니다. 11/2에는 시도 3, 시도 5, 시도 6(이날 오후에 시작), 그리고 본선까지 네 폴더에서 세션이 돌았고, 기록상 커밋은 모두 136개입니다. 이번 글은 대부분 시도 3의 한 시간 이야기입니다.

## 하려던 일

시도 3은 대출 데모의 배포 파이프라인을 만들고 있었고, 그날 오전 "누가 지금 배포해도 된다고 말할 수 있나"라는 문제에 닿았습니다. 먼저 에이전트가 배포 승인의 신뢰 기준을 골라 달라고 했습니다. 기존 조직의 실행 컨트롤러에 연결하거나, 외부 서명 승인과 별도 coordinator를 새로 만드는 두 길이었죠. 저는 기존 컨트롤러를 골랐습니다. 그러자 에이전트가 그 컨트롤러의 API 문서 위치를 물으면서 이렇게 덧붙였습니다. "아직 사용 가능한 컨트롤러가 없다면 '없음'이라고 알려주세요. 존재하지 않는 API를 가정해 구현하지 않겠습니다." 저는 "없음"이라고 답했습니다. 에이전트는 패키징·CI를 먼저 만들고 배포 승인 연동은 보류하자고 권했고, 저도 그렇게 하자고 했습니다. 12시 34분에는 패키징·CI 부분이 독립 검토를 통과했고, 에이전트는 제가 정한 보류 경계에서 멈췄습니다.

그래서 오후 초에 남은 일은 분명했습니다. 보류해 둔 배포 승인 연동입니다.

## 에이전트에게 맡긴 방식

13시 24분, 제가 쓴 건 한 단어였습니다.

> "진행"

에이전트는 제가 배포 승인 연동을 보류했었다는 걸 먼저 짚고, 기존 컨트롤러가 없으니 남은 선택지인 외부 서명 승인 방식(B안)을 실제 서비스 생성·권한 변경·유료 배포 없이 설계와 로컬 구현까지만 하자고 제안했습니다. 승인했습니다. 그다음은 작고 합리적인 질문의 연속이었습니다.

1. **13:42, 서명 방식.** 분리된 관리 환경의 오프라인 서명 도구냐, 중앙 서명 서비스냐. 데모에는 오프라인 도구를 권장했고, 저는 그걸 골랐습니다.
2. **13:51, 공유 실행 기록.** 전용 coordinator API와 별도 Blob 저장소냐, 같은 API에 Cosmos DB냐. 추천은 Blob이었고, 역시 그대로 골랐습니다.
3. **13:53, 상세 설계.** ES256으로 서명한 승인서에 대상, plan·소스·릴리스 해시, 허용 작업, 비용·기간 상한, 만료, 고유 ID를 담습니다. Blob은 coordinator만 수정합니다. 응답이 유실되면 unknown으로 남기고 runner를 바꿔도 우회하지 못합니다. 다음 단계는 별도로 신뢰한 관측 주체의 최신 증거가 있어야 열립니다. "이 설계로 문서 작성"을 골랐습니다.
4. **13:56, 설계 문서.** 한국어로 작성해 커밋했고, 저는 승인하고 구현 계획을 요청했습니다.

26분 동안 승인이 다섯 번이었습니다. 질문마다 에이전트는 실제 키·서비스·클라우드 호출은 아직 만들지 않는다고 분명히 적었습니다. 아마 그 조심성 덕분에 계속 "예"라고 하기가 쉬웠던 것 같습니다. 한 단계씩 보면 다 안전했으니까요. 단계를 모두 더해 보는 일은 아마 저도 하지 않고 있었습니다.

## 어긋난 지점

14시 3분에 plan이 왔습니다. 다섯 작업이었습니다. 서명 계약·도구 → Blob 실행 기록 → coordinator API → 기존 승인 경계 연결 → 관리 코드 격리·운영 인계. 각 작업은 실패 테스트와 독립 검토를 거친다고 했고요.

여기서 멈췄습니다. 저는 "계획 수정 필요"를 골랐습니다. 그걸 읽으며 무슨 생각을 했는지는 기록에 없습니다. 에이전트가 무엇을 고칠지 묻자 제 답은 한 줄이었습니다.

> "무결성 확인 검증은 불필요해 보입니다."

그럼 에이전트는 바로 지웠을까요? 아니었습니다. 제 문장이 서로 다른 두 검사를 한꺼번에 가리킨다고 짚었습니다.

- ① ZIP·소스·의존성 해시 대조 같은 **배포 산출물 무결성 검사**
- ② 승인서 서명과 대상·릴리스 해시를 대조하는 **승인 위조·변경 방지 검사**

①만 빼면 패키징 검증이 단순해지고, ②까지 빼면 방금 고른 외부 서명 승인 구조 자체를 바꿔야 한다는 설명이었습니다. 35분쯤 전에 고른 구조였죠. 저는 둘 다 빼는 쪽을 골랐습니다.

이날 덜어내기는 이것만이 아니었습니다.

**시도 5**는 데모 UI를 만들고 있었는데, 여기서도 제가 세 번 덜어냈습니다.

- 16시 10분, 테스트 실행 화면에 대해: "여기서 테스트를 하는 기능은 모두 불필요해 보입니다."
- 18시 19분: "네트워크 없이 시연 '긴급 동의 철회' 메뉴는 모든 화면에 있을 필요가 없습니다. 삭제해주세요"
- 18시 22분: "'동의 수락부터 5분 뒤 접근을 차단하고 관리 사본을 자동 삭제합니다.' 는 불필요한 프로세스로 보입니다."

재미있는 건 세 번째입니다. 이번에는 에이전트가 한 번 속도를 늦췄습니다. "이번 요청은 문구 수정이 아니라 동의·수집·삭제 정책의 변경입니다." 과제 사례 원문의 '만료 시 자동 삭제' 요건과 달라지니, 이 데모에서는 구현하지 않는다고 설계서에 분명히 적어야 한다고 했습니다. 제가 덜어내고 싶었던 것이 전부 에이전트의 발명은 아니었던 셈입니다. 일부는 과제에서 온 것이었고, 에이전트는 그 사실이 드러나게 해 줬습니다.

**본선**에서는 더 조용한 사례가 있었습니다. 13시 19분, 에이전트가 평가 실행에서 나온 심사 설명 3건을 심사역 입장에서 1~5점으로 채점해 달라고 했습니다. 기준은 세 가지였고, 제 답은 세 건 모두 5/5/5였습니다. 23분 뒤, 브랜치 전체 리뷰를 거친 에이전트가 다시 물었습니다. "앞서 제가 기본값을 5/5/5로 넣어 두어 판단에 영향을 주었을 수 있으니, 아래 신호를 보시고 점수를 다시 확인해 주세요. 그대로 두셔도 됩니다." 함께 보여 준 자동 신호를 보면 세 건 중 두 건이 근거 검사에 실패했습니다. 제가 처음에 세 건을 꼼꼼히 읽었는지는 기록으로 알 수 없습니다. 그 뒤로 새 점수를 낸 기록도 보이지 않고, 다음 답은 "merge"였습니다. 이번에 에이전트가 더한 건 기능이 아니라 기본값이었습니다.

## 넘어간 방법

**먼저 시도 3. 제가 말을 꺼내자 에이전트는 제대로 덜어냈습니다.** 14시 20분, 서명·해시 검증 중심 설계를 철회하고 **사람 확인 + 단일 배포 runner**로 단순화하자고 권했습니다.

- 오프라인 서명 도구, 별도 coordinator·Blob 관리 기반은 만들지 않음
- 실행 전에 대상·예상 비용·작업 목록을 보여 주고 사람이 확인
- 고정된 private runner 한 곳에서만 배포하고, 실행 기록이 없거나 결과가 불명확하면 중단(여러 runner 간 자동 재개는 지원하지 않음)
- 비밀 파일 배제·ZIP 경로 안전성·버전 호환·사설망·동의/삭제 통제는 유지

그리고 이 방식은 승인·산출물의 위변조 방지를 보장하지 않는다는 제한을 문서에 적겠다고 했습니다. 승인했습니다. 14시 24분에 돌아온 수정 spec에는 "기존 복잡한 계획은 폐기했으며"라는 문장이 있었고, 14시 32분의 plan은 다섯 작업이 아니라 세 작업이었습니다. "계획 수정 필요"에서 plan 승인까지 29분 걸렸습니다.

덜어낸 plan도 검토는 제대로 받았습니다. 리뷰에서 서머타임 전환 때 확인 유효기간이 10분을 넘는 문제가 나왔고, 확인이 만료된 뒤에도 토큰 재시도가 요청을 보내는 문제도 나왔습니다. 최종 검토는 Critical 0, Important 3, Minor 1이었고, 모두 고친 뒤 17시 33분에 merge를 골랐습니다. 단순하다고 검증을 건너뛴 건 아니었습니다.

**다음으로 시도 6. 여기서는 처음부터 효율을 물었습니다.** 16시 38분, 시도 3의 설계 문서를 들고 이렇게 시작했습니다.

> "[시도 3의 설계 문서]를 참고해서 어떻게 MVP 를 만드는게 가장 효율적인지 가이드 해주세요."

답의 첫 줄은 이랬습니다. "이 스펙은 범위가 매우 넓습니다(5개 에이전트, 사례 8개, 통제 테스트 약 35개, 사설망 인프라 전체)." 결정론적 코어를 먼저 만들고, 한 사례를 끝까지 연결한 뒤, 사례와 인프라를 넓히자는 순서였습니다. 효율을 직접 물으니 에이전트도 크기 이야기를 한 거죠. 그런데 1분 뒤 제가 한 요청은 "각 단계를 좀 더 디테일하게 확장해주세요"였습니다. 그렇게 나온 plan은 16개 Task였고, 저는 subagent 방식을 골랐습니다. 18시 25분, 테스트 127개가 모두 통과한 채 1단계가 merge됐습니다. 이 일을 위해 새 폴더를 연 이유는 기록에 없습니다.

**이제 본선. 맡기는 방식을 바꿨습니다.** 오전의 평가 단계에서는 에이전트가 추천한 Native 실행(에이전트가 직접 plan을 따라가고 끝에 전체 리뷰를 한 번 받는 방식)을 골랐습니다. 17시 12분에 나온 운영 지표 plan은 14개 Task, 4,605줄이었고, 이번에는 "subagent"를 골랐습니다. Task마다 구현 subagent가 만들고 별도 리뷰어가 검토하는 방식입니다. 첫 수정 라운드는 17시 49분이었습니다. tracing span이 시작하거나 끝날 때 실패하면 계측하는 모든 activity가 실패할 수 있다는 지적이었죠. 18시 17분에는 Task 1~9가 끝났고, Task 5와 9는 수정 한 번 뒤 승인됐습니다.

21시 7분, merge 전에 에이전트가 "내가 대신 내린 결정" 여덟 가지를, 틀렸을 때의 비용과 함께 목록으로 보여 줬습니다. 그중 하나는 서브에이전트 모델이 하네스 기본값이라 "토큰 비용 증가 가능"하다는 것이었습니다. 저는 merge를 골랐고, 결과에서 테스트 878개가 통과했습니다. 돌아보면 13시 56분의 제게 없던 게 바로 이 목록이었습니다. 더해진 것들이 한곳에 모여 있어서, 아직 "아니요"라고 말할 수 있는 상태요.

이날을 돌아보면, 에이전트는 덜어내는 일을 잘 도와줍니다. 아마 혼자 할 때보다 더 꼼꼼하게요. 제 막연한 "불필요해 보입니다"를 구체적인 검사 두 개로 나눠 줬고, 무엇을 포기하는지 문서에 남겼습니다. 하지만 그 한 시간의 승인 행렬에서, 덜어내기는 제가 시작하기 전까지 시작되지 않았습니다.

## 오늘의 교훈

plan이 너무 크다는 말을 에이전트가 먼저 해 주길 기다리지 말자. 승인하기 전에 "데모에 정말 필요한 게 뭔가요?"를 묻고, 덜어낸 것은 에이전트에게 문서로 남기게 하자.
