안녕하세요. 열 번째 일지입니다. 지난 글에서는 시도 7에게 "너무 많이 바꾸고 있지 않나요?"라고 물었는데요, 11월 5일에는 좁히는 일이 한 단계 위에서 일어났습니다. 이날이 끝날 무렵, 나란히 돌던 시도들 가운데 기록을 남기는 건 본선 하나뿐이었습니다.

## 하려던 일

이날 기록이 남은 세션은 넷이었고, 모습이 제각각이었습니다.

먼저 본선. 자정을 막 넘겨 짧게 물었습니다. "남은건 뭔가요?" 답은 구현과 배포는 끝났고 남은 건 데모 준비뿐이라는 것이었습니다. 리허설, 장애 대비 녹화본, 당일 점검. 그런데 답 중간에 정정이 하나 있었습니다. 앞서 미룬 작은 이슈들을 배포 기록에 적었다고 했는데 실제로는 빠져 있어서, 방금 추가하고 커밋했다는 겁니다. 묻지 않았는데도 에이전트가 먼저 바로잡았습니다.

다른 세 시도는 이랬습니다.

- **시도 3**은 Task 아홉 개짜리 계획의 중간이었습니다. 새벽 2시 23분에 Task 7은 끝났고 Task 8은 진행 중이며 Azure 배포나 유료 호출은 하지 않았다고 보고했고, 기록은 거기서 멈춥니다.
- **시도 6**은 그날 밤 한 단계를 통째로 끝냈습니다. 설계, 계획, 구현·리뷰 에이전트로 Task 1–9, 최종 리뷰 지적 3건 반영, 그리고 새벽 1시 58분 master에 squash merge. 테스트는 711개 통과였고 push는 하지 않았습니다. 기록은 여기서 멈춥니다.
- **시도 7**에는 밤 12시 11분에 이렇게 요청했습니다. "azure 환경으로 배포해 주세요"

시도 3과 6이 왜 멈췄는지는 기록에 없습니다. 그래서 짐작하지 않겠습니다. 이날을 끝으로 기록이 없을 뿐입니다.

## 에이전트에게 맡긴 방식

시도 7에서는 단계마다 승인을 받는 방식이 그대로 보입니다. 에이전트는 배포를 막는 문제 두 가지(PC의 Azure CLI 로그인에 기대는 인증, 로컬 HTTP만 허용하는 설정)를 찾고, 고치기 전에 물었습니다. 다음으로 기존 Fabric F2가 이날 0시 37분에 중지돼 있었고, 그 때문에 SQL도 `database disabled`로 접속되지 않는다는 걸 발견했습니다. 재개하면 과금이 다시 시작되니 또 물었고, 저는 재개를 골랐습니다. 그다음 파일 생성 전에 한 번, 실제 생성 전에 한 번 더 물었습니다. Container Apps, 레지스트리, Log Analytics, 관리 ID로 된 작은 호스팅 구성이 월 약 $39.21이고, 호환성 경고 두 개를 따로 적어 두었더군요. 저는 세 항목을 한 번에 승인했습니다.

그사이 본선에는 이렇게 요청했습니다. "로컬 동기화 해주세요" 에이전트가 어디로 동기화할지 되물었고, 공개 GitHub 저장소를 알려 주자 push 전에 민감한 값에 대한 경고부터 들고 왔습니다. 저는 민감한 값을 가린 뒤 원격을 덮어쓰기로 골랐습니다.

아침 7시 57분에는 본선에 새 아이디어를 꺼냈습니다.

> "llm api 호출할 때 api management 가 있어야 할거 같은데 어떤가요?"

여기서부터 승인 양식으로 브레인스토밍이 이어졌습니다. 어떤 방식으로 넣을지, 데모에서 꼭 보여줄 기능(토큰 지표, 단일 경로, 토큰 한도, 콘텐츠 안전을 골랐습니다), 등급은 무엇으로 할지, 콘텐츠 안전에 걸리면 어떻게 할지. 등급은 에이전트가 Developer를 권했습니다. 데모엔 SLA가 필요 없고 비용이 Standard v2의 1/14이라는 이유였습니다. 이어서 네 부분짜리 설계가 나왔고, 저는 부분마다 "네"라고 답했습니다.

## 어긋난 지점

**먼저, 공개 저장소에 비밀값 탐지 경고가 왔습니다.** 새벽 1시 27분, 비밀값 탐지 서비스의 경고를 본선에 그대로 붙여 넣었습니다. "Generic High Entropy Secret" 인시던트 두 건, 각각 공개 저장소의 커밋 두 개를 가리키는 내용이었습니다. 붙여 넣은 경고 위에 제가 쓴 말은 짧았습니다. "하단의 보안 부분에 이슈는 수정해주세요. .gitignore 로 동기화 안해도 됩니다." 아마 경고를 판단하는 일은 에이전트에게 맡겼던 것 같습니다. 제가 직접 따져 본 흔적은 기록에 없습니다.

**다음으로, 코드보다 계획이 오래 걸렸습니다.** API 게이트웨이 spec은 아침 8시 22분에 커밋됐는데, 계획은 11시 4분에야 제게 왔습니다. 그 사이 세션의 체크포인트 제목은 "spec amended"와 "spec finalized"를 두 번 오갑니다. 에이전트가 조사하고 초안을 쓰던 시간입니다.

**실제 환경 조정은 자꾸 멈췄습니다.** 정오 직전에는 Azure 로그인 토큰이 만료돼 APIM 배포를 시작하지 못했습니다. 재로그인 요청을 제가 취소했던 터라, 로그인하고 "로그인했습니다. 게속"이라고 칠 때까지 세션은 그대로 서 있었습니다. 오후에는 세 번, 한 단어만 쳤습니다. "재시도". 원인이 기록에 남은 건 세 번째뿐입니다. 구현 에이전트가 모델 요청에서 DNS를 찾지 못해 다섯 번 재시도 끝에 실패한 것이었죠. 그 직전에는 다른 종류의 문제도 나왔습니다. 주입 시도가 아닌 평범한 심사 케이스가 게이트웨이의 콘텐츠 필터에 막힌 겁니다.

**그리고 시도 7은 과금이 켜진 채로 끝날 뻔했습니다.** 아침 7시 55분, 시도 7에 이렇게 썼습니다. "배포된 Azure 환경을 삭제해주세ㅛ" 8시 26분에 에이전트는 자기가 추가한 호스팅 리소스 4개와 권한 2개를 모두 지웠다고 보고했습니다. 그리고 보고 끝에 굵은 글씨로 한 줄. Fabric F2는 아직 실행 중이라 과금이 계속된다는 것이었습니다.

## 넘어간 방법

**비밀값 경고는 설명을 먼저 듣고, 선택은 제가 했습니다.** 새벽 1시 56분, 에이전트는 실제로 새어 나간 비밀값은 없다고 했습니다. 탐지된 값은 Key Vault용 Azure 기본 제공 역할 ID, 즉 누구나 아는 공개 상수였고, 변수 이름에 "Secrets"가 들어 있어 오탐됐다는 겁니다. 변수 이름을 바꾸고 인프라 테스트 105개를 통과시킨 뒤, 그 값이 남은 과거 커밋 두 개를 어떻게 할지 물었습니다. 저는 이력 재작성을 골랐습니다. 그러자 에이전트는 커밋 228개 전체를 다시 썼습니다. 이때 민감한 값도 함께 가렸고, 이력 전체를 다시 검사해 0건, 최종 파일 내용은 재작성 전과 같음을 확인했습니다. 원본은 세션 폴더에 bundle로 백업하고 force-push했습니다. 그리고 남은 경고를 닫는 건 제 몫이라고 짚어 줬습니다.

**게이트웨이 작업은 계획에 맡겼습니다.** 계획은 Task 0–13이었고, APIM 비용(월 약 $51)과 롤백 스위치가 적혀 있었습니다. 승인하면서 실행 방식으로 하위 에이전트를 골랐습니다. 그 뒤로는 대부분의 Task에 새 구현 에이전트가 붙고, 이어서 리뷰 에이전트가 봤습니다. 실제 Azure를 다루는 Task 4와 11은 컨트롤러 에이전트가 직접 맡았고요. 리뷰에서 되돌아온 건 적어도 세 번이었습니다. Task 6에서는 토큰 한도·rate limit 판별 문자열이 너무 넓다는 지적, Task 9에서는 결과가 비어 있어도 "재현됨"으로 통과한다는 지적, Task 12에서는 네트워크 다이어그램의 닫는 fence가 빠진 것을 비롯한 문서 수정 요청. 모두 수정 라운드와 범위를 좁힌 재리뷰를 거쳤습니다. 실제 환경 검증에서는 계획이 예상하지 못한 것도 나왔습니다. 차단 응답이 403이 아니라 424 안에 403을 담아 돌아와서, 판별 문자열을 하나 더 넣었습니다.

**콘텐츠 필터 오탐은 좁게 고쳤습니다.** 프롬프트 주입 검사를 1만 자가 넘는 프롬프트에서만 건너뛰게 하고, 나중에 정말 위험한 입력은 여전히 막히는지 다시 확인했습니다(`<job-id>` → `content_blocked`).

**멈춘 에이전트는 다시 시키기 전에 상태부터 봤습니다.** 세 번째 "재시도" 뒤, 에이전트는 구현 에이전트가 멈추기 전에 이미 커밋을 마쳤다는 걸 확인했습니다. 인프라 테스트 120개를 직접 돌리고, 보고서가 불완전할 수 있다는 메모를 붙여 리뷰로 넘겼습니다.

밤 9시 50분, 브랜치 전체 최종 리뷰는 "Ready to merge: With fixes"였습니다. Critical은 없고 Important가 셋. 수정 한 번과 재리뷰를 거쳐 9시 59분에는 머지와 push까지 끝났습니다. 에이전트는 비용도 감추지 않았습니다. 신청 1건당 $0.0589가 $0.0939(+59%)로, p95는 1.4분에서 1.8분으로 늘었다고 적었습니다. 그래도 저는 한 번 더 물었습니다. "그럼 적용이 완료된건가요?" 에이전트는 실제 Azure 상태를 확인한 뒤에야 그렇다고 답했습니다.

**이제 시도 7의 남은 하나를 닫았습니다.** 삭제 보고 5분 뒤 "Fabric 은 중지해주세요"라고 썼고, 3분 뒤 F2가 일시 중지됐습니다. 저장소 비용은 따로 나가고, 재개 전까지는 SQL을 쓸 수 없다는 안내도 붙어 있었습니다.

돌아보면, 이날 무언가가 "본선으로 간다"고 정한 기록은 없습니다. 다른 시도들의 기록이 이날 이후로 없을 뿐입니다. 그래도 하나는 분명히 보입니다. 멈추는 것과 닫는 것은 다르다는 점입니다. 시도 6의 마지막 기록은 push하지 않은 로컬 merge입니다. 시도 7에는 살아 있는 리소스가 있었고, 삭제한 뒤에도 F2가 과금 중이라는 걸 에이전트가 먼저 짚었습니다. 닫는 데 든 건 제 짧은 요청 두 개였고, 아마 두 번째 요청은 그 굵은 경고 한 줄 덕분이었을 겁니다.

## 오늘의 교훈

이어 가지 않을 시도는 그냥 두지 말고 닫자. 배포한 건 지워 달라고 하고, 그다음 "아직 과금되는 게 있나요?"까지 묻는다.
