안녕하세요. 지난 글에서는 과제 원문으로 돌아가 기본 질문을 던지며 시도 2를 시작했는데요, 이번 이틀은 그 질문이 설계에서 설계 바깥의 사업 쪽으로 옮겨 갔습니다.

## 하려던 일

10월 29일 점심 무렵, 시도 2에는 이미 로컬 데모가 있었습니다. 에이전트가 남긴 checkpoint 요약을 보면 React·TypeScript·SQLite에 별도 HTTP mock 원천, 그리고 실제 GitHub Copilot SDK 호출까지 붙어 있었고, 최종 리뷰 수정도 끝난 상태였습니다. 데모는 돌아갔습니다. 대신 더 단순한 질문에는 답이 없었습니다. 이게 실제 대출기관에게 의미가 있는 아이디어일까?

그래서 이 이틀 동안은 거의 코드를 요청하지 않았습니다. 29일 커밋 다섯 개는 초기 커밋과 문서, merge였고, 30일에는 커밋이 하나도 없습니다. 대신 사업에 대한 질문을 계속 던지고, 답을 에이전트가 파일로 정리하게 했습니다.

## 에이전트에게 맡긴 방식

먼저, 12시 17분의 첫 요청은 짧았고 오타까지 있었습니다.

> "비지니스 목적으로 분석을 좀 더 해주세ㅛ"

돌아온 답은 프로젝트를 한 문장으로 다시 정리했습니다. 핵심은 "AI가 대출을 승인한다"가 아니라 "작은 대출도 수익성 있게 심사하고, 상환 문제가 커지기 전에 대응한다"라는 것. 그리고 선도 하나 그었습니다. **기술적 동작 확인과 실제 사업성 입증은 별개**라는 것이요. 이어서 사업 책임자, 리스크 책임자, 심사 담당자, 사후관리 담당자, 사업자까지 이해관계자별로 지금의 문제와 줄 수 있는 가치를 표로 정리했습니다. 직접 구매자는 대출기관이고, 최종 수혜자는 소상공인·중소기업이라고요.

30분 뒤 메모 파일로 저장해 달라고 했고, 그대로 저장됐습니다.

다음 날은 한 걸음 더 갔습니다. 원본 문서에서 대출기관의 고객을 설명하는 문장 하나를 짚고 이렇게 물었습니다.

> "이러한 사업을 실제하는 곳이 아시아에 있을까요? 비슷한 사업을 하는 레퍼런스를 찾고 싶습니다."

그다음부터는 짧은 질문이 줄줄이 이어졌습니다. 매번 앞 답을 받아서 다음 질문을 던지는 식이었죠.

1. "각 업체가 어떠한 기술 아키텍처를 사용하는지 알수 있을까요?"
2. "비지니스 가치가 있을지 좀 더 분석해줘"
3. "기존 사업들에 대한 gap 분석을 해주세요. 새롭게 비지니스 가치를 더 높일 방법이나, 디지털 데이터를 통해서 좀 더 신용평가를 잘 할 방법등이 있나요?"
4. "비지니스 차별점을 줄 수 있는 방안이 있을까요?"
5. "플랫폼 업체의 데이터를 어떻게 가지고 와?"
6. "기존의 player 의 문제점이 뭔가요?"
7. "만약 한국의 플랫폼 업체에서 비슷한 레벨의 사업자의 데이터를 구할 수 있다면? (마켓플레이스 셀러 입장에서 대출 요구시 좀 더 명확한 평가가 가능하지 않을까요?)"

중간중간 파일을 업데이트해 달라고 하면, 에이전트가 최근 논의를 두 번째 메모 파일에 반영했습니다.

## 어긋난 지점

**먼저, 조사 도구가 먼저 넘어졌습니다.** 30일 첫 질문 후 6분 안에 tool 호출 세 개가 실패했습니다. GitHub tool의 504, 연결 자체가 안 된 web fetch, 그리고 timeout. 전날에도 GitHub 문서 페이지 하나가 404를 냈고요. 아마 저는 그때 이걸 거의 몰랐던 것 같습니다. 그래도 11시 36분에 답이 왔고, 저장된 파일에는 출처 링크도 들어 있습니다. 다만 결국 어떤 출처까지 닿았는지는 기록만으로는 알 수 없습니다.

**다음으로, 에이전트가 제 주장을 계속 좁혔습니다.** 아마 마음 한쪽에서는 "있습니다, 만드세요" 같은 답을 기대했던 것 같은데요, 답마다 울타리가 쳐져 있었습니다.

- 사례는 실제로 있었습니다. 한국의 이커머스 플랫폼과 캐피탈사의 신용대출, 오픈마켓 판매자 거래 데이터로 시작한 중국의 온라인 은행, 그리고 인도의 대출기관 두 곳. 그런데 **"디지털 거래 기록으로 소기업을 평가한다"는 공통점**과 **"오픈뱅킹·세금·결제 데이터를 모두 동일한 방식으로 사용한다"는 주장**은 구분해야 한다고 했습니다.
- 아키텍처 흐름도는 "공개 자료를 바탕으로 재구성한 논리 구조"이지 각 회사의 원본 설계도가 아니라고 먼저 밝혔고, 비교표에는 "공개 정보의 한계" 열이 따로 있었습니다.
- 사업성은 있다. 다만 새로운 AI 대출기관이 아니라, 기존 대출기관에 파는 심사 준비·사후관리 업무 솔루션으로. 제한된 유료 파일럿을 추진할 근거는 있지만 수익성이 검증된 건 아니라고 했습니다. 그 답에 이런 제목이 있었습니다. "경쟁사 사례는 시장의 증거이지, 우리 제품의 경쟁력은 아닙니다"
- gap 분석에서는 "공개되지 않은 기능을 해당 업체에 없는 기능이라고 단정하지는 않습니다"라고 미리 적었습니다.
- 비슷한 판매자와 비교하자는 제 아이디어에도 맥락이 생긴다고 동의하면서, 둘로 나눴습니다. 영업 상태를 더 명확하게 평가하는 것과 대출 상환위험을 더 정확하게 예측하는 것은 다르고, 뒤쪽은 현금·기존 채무·실제 상환 결과가 더 있어야 한다고요.

실패라고 할 일은 아니었습니다. 다만 응원은 아니었죠.

**그리고 저장 하나가 빠졌을 수도 있습니다.** 12시 34분에 두 번째 메모 파일을 업데이트해 달라고 했는데, 기록에 답이 보이기 전인 1분 뒤에 제가 사업성 질문을 먼저 던졌습니다. 다음 저장(13시 18분)의 요약에는 사업성 분석을 추가했다고 되어 있고, 그다음 저장(14시 19분)에는 gap, 차별화, 플랫폼 데이터 확보, 동종 판매자 비교가 나옵니다. 12시 27분의 아키텍처 비교는 어느 요약에도 없습니다. 실제로 파일에 들어갔는지는 기록만으로는 알 수 없습니다.

## 넘어간 방법

**좁혀지는 답에는 계속 물었습니다.** 단서에 반박하지 않고, 그 단서 안에서 다음 질문을 던졌습니다. "AI로 더 정확하게 신용평가합니다"로 정면 승부하려면 실제 상환·부실 데이터가 필요하다는 말을 듣고는 gap이 어디냐고 물었고, 온라인 판매자 대상 "정산 흐름 기반 심사·상환 설계 지원"이 나오자 그럼 플랫폼 데이터는 어떻게 가져오냐고 물었습니다. 그 답은 **"사업자가 동의했다"와 "플랫폼 데이터를 금융 심사에 사용할 권한이 있다"는 별개**라고 나눠 줬습니다. 아마 이 이틀 동안 나온 것 중 가장 쓸모 있는 건 이 여덟 개 질문의 흐름이었던 것 같습니다.

**기억은 파일에 맡겼습니다.** 이틀 동안 다섯 번 저장이나 업데이트를 시켰습니다. 기록에 남은 답마다 무엇을 넣었는지 짧은 요약이 붙어 있었고, 위의 빈틈도 그 요약 덕분에 보입니다. 요약을 내가 요청한 것과 맞춰 보는 확인 한 번, 이걸 더하면 좋겠다 싶습니다.

**곁가지 일에서도 같은 모습이 보였습니다.** 29일에 시도 2를 Copilot에 로그인된 것과 다른 GitHub 계정으로 올리고 싶었습니다. 그래서 이렇게 물었죠.

> "현재 로그인된 [Copilot] 은 그대로 쓰고 github 동기화 할때만 `<sync-account>` 사용자를 써서 `<sync-account>` 리포지토리로 동기화 하는것도 가능할까요?"

첫 답은 일반적인 방법이었습니다. 동기화 계정 전용 SSH 키를 만들어 이 저장소에만 지정하라는 것. 알아 둘 만한 주의도 두 개 붙었습니다. 원격 주소만 바꾼다고 인증 계정이 바뀌지는 않고, `user.name`·`user.email`은 커밋 작성자 정보이지 로그인 인증이 아니라는 것.

그럼 제가 한 일은요? 사실 하나를 더 알려 줬습니다. "현재 `<sync-account>` 도 로그인이 되어 있는 상태에요. gh 에". 에이전트는 확인 후 두 계정 모두 정상 인증되어 있다고 하고, 계획을 바꿨습니다. 새 로그인도, SSH 키도, 전역 `gh auth switch`도 필요 없다고요. 아직 원격 저장소가 등록되어 있지 않다는 것, 설정은 바꾸지 않았다는 것도 같이 알려 줬습니다. 푸시 전에는 한 번 더 물었습니다. 대상은 공개 저장소이고 `main`에는 README만 있으며, 로컬에는 커밋하지 않은 분석 문서 13개가 있는데 어떻게 동기화할지. 저는 `main`을 골랐고, 3분 뒤 데모 코드와 문서가 올라갔습니다. 기존 이력은 보존됐고, 제 활성 계정도 그대로였습니다.

이제 마지막입니다. 그날 오후에는 제 설계를 설명하는 데도 에이전트를 썼습니다. orchestration 문서를 brainstorming으로 보강해 달라고 했더니, 손대기 전에 문서는 별도 LLM Orchestrator를 가정하고 있지만 실제 데모는 코드가 5개 역할을 내부 함수로 연결하고, 그중 3개만 LLM을 쓴다는 차이를 짚었습니다. 문서의 주된 목적을 묻길래 `conceptual`(개념 설명)을 골랐습니다. 이어서 내놓은 보강안의 핵심은 이 한 줄이었습니다. 5개 에이전트는 5개 업무 역할이며, 반드시 5개의 LLM이나 별도 서버를 만드는 것은 아니다.

돌아보면, 이 이틀은 손은 덜 쓰고 질문은 많이 한 날이었습니다. 에이전트가 좋은 리서치 동료였던 건 제 말에 맞장구를 쳐서가 아니라, 근거가 어디서 끝나는지 계속 표시해 줬기 때문입니다. 그리고 다시 쓸 수 있는 건 결국 파일로 남은 부분이었습니다.

## 오늘의 교훈

만들지 않는 날에는 에이전트를 조사 상대로 쓰고, 답은 파일로 남기자. 그리고 저장이 정말 됐는지 요약으로 한 번 확인하자.
