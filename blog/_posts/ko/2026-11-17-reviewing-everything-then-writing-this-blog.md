안녕하세요. 지난 글에서 본선은 기능에서 산출물로 넘어갔습니다. 이번 글은 기록에 남은 마지막 날, 11/17 이야기입니다. 이날은 반으로 나뉘는데요, 오전에는 코드 전체를 한 번 더 리뷰해 달라고 했고, 점심 무렵에는 지금 읽고 계신 이 블로그를 같이 쓰자고 했습니다.

## 하려던 일

시작은 뒷정리였습니다. 아침 9시에 "커밑해주세요"(오타 그대로)라고 쳤고, 에이전트가 아키텍처 다이어그램을 커밋했습니다. 국문판·영문판·에이전트 강조 영문판, 파일 29개였어요. 푸시하겠냐는 물음에는 "네".

그리고 1분 뒤 진짜 요청을 했습니다. 데모는 이미 배포돼 돌아가고 있었는데요, 아마 장표까지 끝낸 김에 기능 단위로 만들면서 놓쳤을 문제를 마지막으로 한 번 훑고 싶었던 것 같습니다.

## 에이전트에게 맡긴 방식

> "전체적으로 소스를 리뷰 및 최적화 해주세요"

크고 막연한 한 문장이죠. 에이전트는 바로 달려들지 않았습니다. 먼저, 방금 푸시가 GitHub token 만료로 실패했으니 다시 로그인해 달라고 알렸습니다. 다음으로 규모를 알려 줬습니다. Python 약 4.4만 줄, Bicep 약 3,300줄. 그러고는 범위를 고르라는 승인 양식을 띄웠고, 저는 보기 네 개(버그·로직 오류 / 보안: 가명처리·인증·네트워크 / 성능·지연 / 코드 정리)를 모두 고르고, 범위는 전체, 방식은 "fix"로 답했습니다.

여기서부터가 제가 그대로 따라 하고 싶은 부분입니다. 9시 10분, 에이전트는 코드를 네 영역으로 나눠 리뷰어 넷을 한꺼번에 보냈습니다.

- 오케스트레이터와 에이전트들
- Policy Engine, mock API, 평가, 운영 도구
- 심사역 콘솔
- Bicep 인프라

지시문마다 같은 규칙이 박혀 있었습니다. 읽기만 할 것, 파일이나 브랜치는 건드리지 말 것, 다른 에이전트를 띄우지 말 것, 코드를 읽고 확신하는 것만 보고할 것(파일·줄, 실제로 터지는 시나리오, 고칠 방법), 마지막에 판단을 보류한 것을 적을 것. 그 사이 에이전트는 전체 테스트를 돌려 기준선을 잡아 뒀습니다.

결과는 9시 16분부터 19분 사이에 들어왔고, 넷 모두 Critical은 없었습니다.

- **콘솔:** Important 2개, Minor 8개. XSS·CSRF·open redirect 문제는 없음.
- **운영·정책:** Policy Engine에는 막는 결함 없음. 다만 `window close`가 실패해도 "닫힘"으로 보일 수 있고, 생성한 비밀값이 오류 메시지에 찍힐 수 있음.
- **인프라:** API Management 구독을 하나 더 쓰면 에이전트별 token 한도를 우회할 수 있고, Key Vault 비밀 접근 권한이 필요 이상으로 넓음.
- **오케스트레이터:** Important 3개, Minor 5개. 가장 심각한 건 심사역이 자유롭게 쓴 사유가 가려지지 않은 채 모델로 갈 수 있다는 것.

에이전트는 가장 느린 리뷰어를 기다리지 않았습니다. 9시 18분에 수정 에이전트 셋을, 19분에 넷째를 보냈습니다. 수정 쪽 지시문은 리뷰어보다 더 엄격했습니다. 자기 영역 폴더만 고칠 것(나머지는 다른 에이전트가 고치는 중이니까), 커밋·스테이징·푸시·배포 금지, 동작을 바꾸면 실패하는 테스트부터 쓸 것, 그리고 "if a finding is wrong, skip it and say why". 심사역 채팅 가명처리는 오케스트레이터와 콘솔 두 영역에 걸쳐 있어서, 그 조각은 에이전트가 직접 하겠다고 남겨 뒀습니다. 지난 글에서 병렬 에이전트들이 서로 덮어쓰던 일을 기억해서였는지는 모르겠지만, 이번엔 영역마다 주인이 딱 하나였습니다.

## 어긋난 지점

**먼저, 울타리가 조금 샜습니다.** 오케스트레이터 수정 에이전트는 평가 테스트 하나가 실패하는 걸 봤는데, 그 파일은 다른 에이전트가 고치는 중이라 그대로 두었습니다. 운영 쪽 수정 에이전트는 자기 영역 밖 테스트 하나를 깨뜨렸는데, 의도한 결과라고 했습니다. mock 재시작 뒤 동의를 철회하면 이제 404 대신 철회가 기록된다는 거였죠. 둘 다 울타리를 넘어가 고치지 않고 보고만 했고, 실제로 바뀐 기대값 하나는 메인 에이전트가 고쳤습니다.

**다음으로, 또 배포 날이었습니다.** 11시 52분에 에이전트가 정리해 줬습니다. 커밋 4개, 테스트 5,253개 통과, 최종 리뷰 문제 없음. 그리고 다음에 뭘 할지 물었고, 저는 "푸시 + 배포 + 스모크"와 예전 Key Vault 역할 삭제를 골랐습니다. 그다음은 익숙한 목록입니다.

- 첫 배포는 이미지 빌드 중 az token 연결이 끊겨 실패. 다시 돌리니 성공.
- Functions 배포는 403. 이 PC가 나가는 주소가 하나 더(`<my-ip>`) 있었기 때문입니다. 임시 규칙으로 통과시키고, 끝난 뒤 규칙을 지웠습니다.
- 첫 smoke는 콘솔 확인에서 시간 초과. Application Gateway가 또 중지돼 있었습니다. 에이전트가 게이트웨이를 켜고 예전 역할을 지운 뒤 다시 돌렸고, 더 좁은 Key Vault Reader 역할만으로 통과했습니다.

**그리고 언어.** 그 세션의 규칙은 답을 한국어로 하는 거였는데, 12시 43분 보고가 영어로 왔습니다. "답변을 한글로 주세요"라고 했죠. 10분 뒤 이 블로그 브레인스토밍의 첫 답도 영어로 와서, 한 번 더 세게 썼습니다. "답변은 반드시 한글로 주세요." 왜 그랬는지는 모릅니다. 기록에는 그랬다는 것만 남아 있습니다.

그 사이에는 자주 그랬듯 "ip 확인 후 콘솔 접속 가능하게 해주세요"도 한 번 했고요.

## 넘어간 방법

**마지막 리뷰어 하나를 전체 변경에.** 에이전트는 끝났다고 하기 전에 수정을 영역별 커밋 4개로 묶고, 독립 리뷰어 하나를 더 보내 전체 diff를 읽게 했습니다. 질문은 다섯 개를 콕 집었는데, 예를 들면 새 API Management 검사가 실제 게이트웨이 연결을 깨뜨리지 않는지, Key Vault 역할을 잃은 쪽 중에 아직 그 역할이 필요한 곳은 없는지 같은 것들이었습니다. 10시 9분 답은 "No significant issues found". 전체 테스트는 5,253개 통과, 140개 건너뜀.

**이제 블로그입니다.** 배포가 끝난 12시 52분, `/superpowers:brainstorming`을 열고 이렇게 썼습니다.

> "단순 기술 블로그가 아니라 처음 agent 개발을 해보는 사람의 시행착오 스토리 같은 형태로 해보고 싶은데 어떻게 하는게 좋을까요?"

에이전트는 약속부터 하지 않고 자료부터 확인했습니다. 10/31 이후 커밋 436개, 배포 이력 35건, 10/26부터의 세션 로그, 저장된 요약 182개. 화자·글 구성·날짜 묶기·민감 정보 처리처럼 스스로 채울 수 있는 건 채운 뒤 "틀리면 고쳐 주세요"라고 했습니다. 블로그를 둘 곳은 세 가지 안을 내밀며 전용 저장소를 추천했는데, 저는 이 저장소 안 폴더인 3번을 골랐습니다. "향후 변경될 수 있겠으나 우선 3번으로 해주세요." 다른 폴더의 세션 기록을 찾아내고는 넣을지 물었고, 답은 "다른 시도들도 넣어주세요".

설계 문서를 보여 주기 전에는 리뷰어 하나에게 "저자와 이야기할 수 없는 구현자" 입장에서 읽게 하고, 잘못 짐작하면 문제가 될 질문만 뽑게 했습니다. 제게 돌아온 건 익명 여부와 브랜치, 두 가지. 나머지(다른 시도 저장소는 링크하지 않기, 이미 공개된 ID도 가리기, 첫 편으로 문체 확인받기, 질의응답 세션은 제 말과 에이전트 답만 쓰기)는 에이전트가 정하고 알려 줬습니다. 계획은 작업 7개에 제 승인 관문 3개(목차, 첫 편 문체, 푸시 전 최종 검토)였고, 저는 "서브에이전트 방식으로 진행"이라고 답했습니다.

그럼 오전과 같은 모양이 다시 나옵니다. 작업마다 새 구현 에이전트, 그다음 리뷰어. 이 글들에서 ID·경로가 새는지 잡는 검사기는 첫 리뷰에서 놓친 경우 3개가 나왔습니다. 원래 구현 에이전트는 이미 끝나 있었고("Agent not found"), 에이전트는 지적 사항을 들려 새 에이전트를 보냈습니다. 새 에이전트는 실패하는 테스트부터 쓰고 고쳤고, 짧은 재리뷰가 지적 하나하나를 확인했습니다. 사이트 뼈대는 이 PC에 Ruby가 없어 로컬 Jekyll 빌드 없이 만들어졌고, 첫 실제 빌드는 GitHub Actions에 맡겨졌습니다.

그 뒤 일은 이날 기록 밖이라 짧게만 적겠습니다. 16편 목차는 수정 없이 승인됐습니다. 첫 편 문체 관문을 지난 뒤 작성 규칙에 한 줄이 더해졌습니다. 기록에 없는 제 속마음이나 행동을 쓰지 말고, 짐작이면 "아마"라고 쓸 것. 그리고 어떤 시도를 왜 접었는지 기록에 없는 곳에서는, 이 글들도 그 시도의 기록이 어디서 멈췄는지만 적었습니다.

돌아보면, 이 연재는 10/26에 login 오류를 두고 "그 상태를 확인해줄래요?"라고 묻는 데서 시작했습니다. 그 뒤로 '진행' 전에 '왜요?' 묻기, 같은 요청을 세 폴더에, 다섯 폴더를 동시에, 그리고 하나로 좁히기. 가격부터 묻기, 질문은 다른 세션에서, 병렬 에이전트에게는 항목마다 주인 하나. 끝까지 안 바뀐 것도 있습니다. 자주 IP를 확인해 콘솔을 열어 달라고 했고, 결정은 늘 승인 양식으로 제게 돌아왔습니다. 마지막 날의 리뷰는 그 전부를 요약한 모양이었습니다. 영역별로 나누고, 리뷰어는 읽기만 하고, 수정 에이전트에겐 울타리를 치고, 승인이 필요한 단계는 제게 남겨 두는 것.

## 오늘의 교훈

큰 리뷰는 영역별로 나누고, 리뷰어는 읽기만 하게, 수정 에이전트에겐 각자 울타리를 쳐 주자. 그리고 푸시·배포·최종 판단은 끝까지 내가 쥔다.
