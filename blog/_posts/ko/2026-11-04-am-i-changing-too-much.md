시도 7에서 계속 진행을 승인하다가 변경 규모를 수치로 요청했다. 커밋된 변경만 52개 파일, 약 2.2만 줄이었다. 줄 수 자체가 결함은 아니지만, 무엇이 필수 경로에 속하는지 다시 판단할 만큼 검토 범위가 커져 있었다.

## 작업 목표

시도 7의 목표는 기존 대출 MVP를 동의 우선(consent-first) 5-Agent 구조로 키우는 것이었습니다. 업무 오케스트레이터가 Consent Lifecycle을 항상 먼저 부르는 구조예요. 에이전트는 격리된 worktree에서 작업하고 있었고, 원래 MVP는 그대로 두는 조건이었습니다.

먼저, 자정을 막 넘겨 확인 질문을 하나 했습니다.

> "지금 구현은 기존 mvp 를 포함한 개선인거죠? 아니면 기존 mvp 를 고려안하고 새로 구현인가요?"

답은 분명했습니다. "기존 MVP를 기반으로 한 단계적 개선"이라는 것. 화면, 채팅, 데이터, 배포 환경은 유지하고 동의·철회·삭제와 Agent 실행 기반을 새로 만든다고 했습니다. 그리고 새 Agent 흐름은 *아직* 기존 신청 화면에 연결되지 않았다는 말도 덧붙였고요. 저는 "네 진행"이라고 답했습니다.

다음으로 오전이 지나갔습니다. 08:01부터 12:53까지 저는 "진행"을 다섯 번 보냈습니다. 그때마다 짧은 보고가 돌아왔습니다. 커밋 하나와 무엇을 더했는지, 그리고 대부분 "실제 Azure 변경은 하지 않았습니다"라는 한 줄. 중간에 승인 양식이 두 번 떴습니다. 한 번은 WSL에 x86 에뮬레이션을 설치해도 되느냐(제 시스템 설정을 바꾸는 일이라서요)였고 저는 승인했습니다. 다른 한 번은 이미지 빌드가 QEMU 충돌과 Podman 제한에 막히자 시스템 변경을 더 허용할지 묻는 것이었는데, 이번엔 코드 작업만 계속하는 쪽을 골랐습니다.

보고 내용은 Fabric 생성 코드, 배포 CLI, SQL 초기화, Agent 게시 CLI, 모델 예산 연결, 로컬 컨테이너 이미지 검사 같은 것들이었습니다. 하나씩 보면 다 그럴듯했습니다. 아마 그래서 전체 크기가 눈에 안 들어왔던 것 같습니다.

## 요청 범위와 수행 절차

오후 1시 30분, 드디어 물었습니다.

> "현재 status 는 어떻게 되나요? 혹시 너무 많은 변화를 하고 있지는 않나요?"

답의 첫 줄은 "네, 우려하실 만합니다"였습니다. 5개 Agent의 업무 연결보다 운영·배포 안전장치 구현 쪽으로 비중이 커졌다는 설명과 함께 표와 숫자가 왔습니다.

- 기존 MVP: 유지 중. 새 작업은 별도 브랜치에 있고 병합 전.
- 구현된 것: Consent Lifecycle과 동의 우선 처리, 인증·저장·재시도·철회/삭제·모델 호출 예산.
- 안 된 것: 새 설계의 나머지 Agent 4개, 기존 MVP와의 통합, 실제 배포.
- 규모: **커밋된 것만 52개 파일, 약 2.2만 줄 추가.** 애플리케이션 코드 약 8,300줄, 테스트 약 8,400줄, 의존성 잠금 파일 약 5,300줄. 본인 표현으로는 "작은 MVP 개선이라고 보기에는 상당한 규모"였습니다.

원인도 짚었습니다. 배포 자동화와 검증 체계를 먼저 깊게 만들면서 범위가 커졌다는 것. 권고는 추가 인프라 확장을 멈추고 "동의 확인 → 기존 MVP 분석 → 심사 결과 표시"라는 최소 흐름부터 연결한 뒤, 필요한 Agent를 하나씩 더하자는 것이었습니다.

그럼 제 답은요? 1분 뒤 보낸 메시지는 그 권고를 거의 그대로 옮긴 문장이었습니다. 에이전트는 이걸 범위가 정해진 승인 양식으로 바꿔 왔습니다. 수정은 동의 단계 분리와 관련 테스트로 한정하고, 새 DB·리소스·배포 자동화는 넣지 않는다는 내용이었죠. 저는 바로 승인하지 않고 되물었습니다.

> "해당 설계가 agent 관점에서 orchestration 이 포함된건가요?"

아마 줄이다 보면 "에이전트다운" 부분이 빠질까 봐 걱정했던 것 같습니다. 답은 "네"였습니다. 기존 workflow 서비스를 업무 오케스트레이터로 쓰고, 순서·조건·재개는 Python 코드가 제어하며, 분석 Agent는 지금처럼 LLM과 tool을 씁니다. 동의 판단이나 실행 순서를 LLM에 맡기지는 않고요. 분산 실행은 보류였습니다.

"네 진행해주세요." 23분 뒤 커밋이 올라왔습니다. 업무 코드 변경은 4개 파일, 새 인프라·DB·화면은 없었습니다.

## 관찰된 문제

"그럼 이제 테스트 해보면 되나요?" 바로는 아니었습니다. 수정본으로 서버부터 다시 띄워야 했거든요. 오프라인 테스트는 1,334개 통과했고, 실제 Fabric·Foundry 연동은 비용이 생길 수 있어 따로 승인이 필요했습니다. "테스트해보게 준비 및 가이드 해주세요"라고 하자 승인 양식이 떴고, 저는 기존 리소스로 실제 연동 테스트를 하고 F2는 제가 직접 멈추는 쪽을 골랐습니다. 에이전트는 그러면 F2가 계속 과금되니 테스트가 끝나면 알려 달라고 했습니다.

첫 테스트 건 SME-001이 처리오류로 떴습니다. "SME-001 이 처리오류로 나오는데 왜인가요?" 원인은 SQL 하트비트 오류(`HEARTBEAT_FAILED`)였습니다. 동의 확인, 데이터 조회, LLM 호출은 다 성공했고 Spark 분석 전에 멈췄다고요. 다만 당시 SQL 세부 오류 코드가 로그에 없어서 연결 장애인지 DB 잠금인지는 아직 확정할 수 없다고 했습니다.

아마 이때 흔들렸던 것 같습니다. 오후 2시 40분에 이렇게 물었거든요.

> "지금 개발되던것을 버리고 이전 환경으로 롤백 가능한가요?"

답은 "네, 가능합니다"였고 순서도 적어 줬습니다. 그런데 단서가 붙었습니다. 같은 하트비트 처리 코드가 이전 MVP에도 똑같이 있어서, 롤백만으로 이 오류가 해결된다고 보장할 수는 없다는 것. 서버 중지나 삭제는 아직 아무것도 하지 않은 상태였습니다.

3분 뒤 다른 게 눈에 들어왔습니다. "UI 도 다른거 같은데요? 맞나요?" 맞았습니다. 이전 사이드바·대시보드·스타일 개선은 원본 폴더의 *미커밋* 변경이었는데, 새 worktree는 커밋 기준으로 만들어져서 그게 빠져 있었던 겁니다. 에이전트는 "기존 UI를 그대로 사용한다"고 했던 이전 안내가 부정확했다며 사과했습니다.

## 대응과 결과

결국 롤백은 하지 않았습니다. 대신 "이전 사이드바·대시보드·스타일 개선을 현재 작업중인 branch 도 활용할 수 있게 할 수 있나요?"라고 물었습니다. 에이전트는 범위를 좁게 그었습니다. 원본의 UI 파일 13개(스타일·템플릿·아이콘·화면용 JS)와 관련 테스트만 옮기고, 원본 폴더와 동의·분석 로직은 건드리지 않으며, 하트비트 오류 수정은 이번 범위에 *넣지 않는다*. 승인했고, 오후 3시 22분에 커밋됐습니다.

이제 오류 차례입니다. 오후 4시 1분, "처리 오류를 분석해서 버그를 잡아주세요." 에이전트는 재현 전에 먼저 물었습니다. 기존 테스트 SQL에 별도 합성 검증 run을 만들고, 필요하면 SME-001 한 건을 실제 LLM·Spark로 돌려도 되느냐고요. 기존 기록은 지우지 않는다는 조건이었습니다. 승인하자 실제 SQL 연결 오류를 한 번 주입해 수정 코드가 새 연결로 복구되는 걸 확인했고, 새 SME-001도 분석까지 마쳤습니다. 최종 수정은 일시적 오류를 최대 2회 재시도하는 것이었고, 처음 오류의 세부 원인은 역시 로그가 없어 확정하지 못했다고 밝혔습니다.

저녁에는 "이 환경을 azure 로 배포한다면 구성은?"이라고 물었습니다. 기존 Fabric·Foundry는 그대로 두고 웹 프로세스만 Container Apps로 옮기면 되고, 보류한 5-Agent 인프라를 "다시 확장할 필요는 없다"는 답이었습니다.

같은 날 본선은 정반대로 흘러갔습니다. 이번엔 범위를 넓힌 쪽이 저였거든요. 오후에 정책상 거절이어도 확인 팝업을 거쳐 심사역이 승인할 수 있게 해 달라고 했고, 한 시간이 안 돼 배포됐습니다. 그리고 17:32부터 17:56까지 요청을 연달아 넣었습니다.

- 고객용 신청 페이지
- 사후 재생 일시정지
- 심사역용 그래프 추가
- 조건부 승인 제외
- 운영 지표 확대
- "최대 대출은 6개월로 변경해주세요"
- 마켓플레이스 셀러 이름과 실제 같은 데이터
- 신청 상세 화면 탭
- 사후 모니터링 데이터 현실화

에이전트는 바로 코드를 쓰지 않았습니다. 요청들을 합치면 정책 규칙과 메시지 계약이 함께 바뀐다며 **architectural**로 분류하고, P9라는 한 단계로 묶어 spec부터 썼습니다. 6개월 요청에는 어디까지 적용할지 되물으면서, 기간이 줄면 월 상환액이 약 2배가 된다고 경고했고요. 저는 12개월 유지를 골랐습니다. 이어서 태스크 15개짜리 plan, 117개 파일을 본 브랜치 전체 리뷰, 중요 이슈 3건 수정. 밤 11시 56분에 병합과 배포까지 끝났고 테스트는 1,350개 통과였습니다.

이쪽도 작은 변경은 아니었습니다. 아마 차이는 "보였느냐"였던 것 같습니다. 본선에서는 추가할 때마다 질문으로 돌아왔고, 이름 붙은 단계 안에 담겼습니다. 시도 7에서는 "진행"이 이어지는 동안 범위가 자랐고, 전체 크기는 제가 물었을 때에야 보였습니다.

다른 시도에서도 같은 장면이 있었습니다. 시도 3에 "아직도 진행중인가요?"라고 물었더니, 테스트가 무한 대기에 멈춰 있었다며 늦게 확인해 죄송하다고 했습니다. 1시간이 안 돼 "진행중인가요?"라고 다시 물었을 땐, 실제로는 작업 중이 아니었고 앞서 말한 "진행 중"은 전체 계획이 덜 끝났다는 뜻이었다고 사과했습니다. 시도 6에 "전체 구현이 다 된건가요?"라고 묻자 "아니요"와 함께 남은 단계 표가 왔습니다.

돌아보면, "진행"은 작은 걸음에는 괜찮은 답이었습니다. 다만 가끔은 멈춰서 변경이 얼마나 커졌는지 물어야 했습니다. 느낌 말고 숫자로요. 처음 해 보는 분이라면, 이 질문 하나만 일정에 넣어 두셔도 충분합니다.

## 오늘의 교훈

"지금 변경이 얼마나 커졌나요?"를 주기적으로 묻자. 에이전트는 숫자로 솔직하게 답한다. 단, 물어볼 때만.
