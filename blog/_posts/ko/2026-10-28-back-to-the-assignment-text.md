첫 번째 MVP가 Azure에서 계속 동작하는 동안 두 번째 저장소에는 과제 원문을 놓았다. 이번에는 실행 중인 기능 목록을 출발점으로 삼지 않았다. 에이전트의 설계 답변이 원문의 어느 요구에 대응하는지부터 확인했다.

## 작업 목표

먼저 시도 1은 전날 밤 멈춘 자리에서 다시 시작했습니다. 새 화면을 반영하기 전 점검에서, 에이전트가 Fabric F2 용량이 Paused 상태라 SQL 연결이 막혀 있다는 걸 찾아냈습니다(오류 42131). 그리고 멈춰서 물었습니다. 용량을 재개하면 과금이 다시 시작되는데 진행할까요? 진행을 골랐고, 오전 8시 4분에는 새 화면이 제 PC에서 떠 있었고 GitHub `main`에도 병합돼 있었습니다.

그러면서도 하루 동안 저는 이미 만든 것에 대해 계속 묻고 있었습니다. 오후 2시 14분에는 이렇게요.

> "지금 fabric 으로 json 을 밀어넣고 그걸 medalion architecture 방식으로 정제해서 AI 가 사용하는데 일반적으로 권장되는 아키텍처인가요? 다른 더 좋은 대안이 있을까요?"

에이전트의 답은 "네"였습니다. Fabric을 분석 플랫폼으로 쓴다면 Bronze → Silver → Gold는 Microsoft가 권장하는 패턴이라고요. 다만 "데이터 정제에 좋은 구조"와 "고객 신청을 빠르게 처리하는 구조"는 구분해야 한다며 하이브리드 구조를 제안했습니다. 아마 저는 집을 다 지어 놓고 나서야 기초가 맞는지 확인하고 있었던 것 같습니다.

시도 2는 순서가 반대였습니다. 질문이 먼저, 코드는 나중.

## 요청 범위와 수행 절차

오후 1시 59분에 사례 문서 이미지를 붙이고 영어 원문을 markdown 파일로 만들어 달라고 했고, 이어서 한국어 번역본을 다른 파일로 만들어 달라고 했습니다. 그다음이 이 요청이었습니다.

> "@ko-origin.md 파일을 분석해주세요"

그 뒤로 오후 내내 짧은 질문이 이어졌습니다. 쓸 만한 답이 나오면 번호를 붙인 분석 파일로 저장해 달라고 했습니다. 질문은 대부분 기본적인 것들이었습니다.

- 카드·PG 정산은 오픈뱅킹 mock에서 확인할 수 있나, 아니면 따로 만들어야 하나? (상세 내역은 별도 mock으로.)
- 은행 데이터와 정산을 전부 대사하는 건 너무 번거로워 보이는데, 대안은? (은행 계좌를 현금흐름의 유일한 기준으로 두고, 정산은 거기에 더하지 않는다.)
- "PG 정산은 향후 받을 돈이라 평가할 때 중요한 포인트 아닌가요?" 에이전트의 답은 "맞습니다. 앞선 제안은 '이미 발생한 현금흐름'에만 초점을 맞춰"로 시작했습니다.

다음으로, 모든 일의 시작이 된 질문입니다. 오후 3시 22분이었습니다.

> "Capston project 에서 5개의 agent 를 만들어야 한다고 되어있는데 이게 다 LLM agent 여야 하나요?"

반드시 그렇지는 않다는 답이었는데, 대화 안에 과제 명세가 없어서 무엇이 5개에 들어가는지는 확정할 수 없다고 덧붙였습니다. 그래서 "5개 에이전트의 협업이 요구사항입니다."라고 알려 줬습니다. 그다음엔 같은 종류의 질문을 영어 원문에 대고, 또 평가 기준에 대고 다시 했습니다. 평가 기준은 markdown으로 만들고 한글로 옮겨 둔 상태였고요. 원문 기준으로 Data Assembly Agent는 LLM일 필요가 없고, 평가 기준에는 모든 에이전트를 LLM으로 만들라는 조건이 없으며, 5개라는 숫자는 평가 기준이 아니라 과제 자체에서 온 것이라는 답이었습니다.

## 관찰된 문제

그날 오후에만 세 번, 에이전트의 답이 제 뜻에서 비켜 갔습니다.

**먼저, 프로젝트를 줄여 버렸습니다.** 오후 3시 31분, 5개 협업이 요구사항이라고 하자 에이전트는 "현재 MVP에 맞춘" 에이전트 5개를 제안했습니다. 데이터 검토, 현금흐름 분석, 정산·유동성 전망, 리스크 검토, 심사 보고서. 사례 문서의 다섯 역할은 하나도 없었습니다. 15분 뒤인 3시 46분, 추천받은 ‘LLM이 필요한 판단은 에이전트에, 정확성과 통제가 필요한 처리는 코드 도구에’ 맡기는 혼합 구조를 어떻게 짜는지 물은 데 대한 답도 같은 축소판을 기준으로 하면서 원문의 채권 회수·동의 수명주기 역할은 유지하지 않는 구성이라고 적었습니다.

**다음으로, 다른 화면을 설명했습니다.** 오후 4시 52분에 client 화면을 어떻게 구성하면 좋을지 물었더니 담당자용 업무 콘솔을 설명했습니다. 제가 말한 건 사업자가 신청하는 사업자 포털이었는데요.

**그리고 한꺼번에 너무 많이 설명했습니다.** 오후 내내 저장소, API, Durable Functions, 오케스트레이터 이야기를 들은 끝에, 5시 56분에 이렇게 썼습니다.

> "지금 아키텍처가 정확히 이해가 안되요. 어떤식으로 하면 좋을까요?"

한편 시도 1은 저녁에 다른 종류의 문제를 만났습니다. 밤 9시 5분, 한 신청 건이 정규화·검증 단계에서 `REMOTE_FAILURE` 한 줄만 남기고 실패했다고 에이전트에게 알렸습니다. 에이전트는 읽기 전용으로 진단했습니다. 수집과 Bronze 저장은 성공했고, 밤 9시 2분~3분 사이에 Fabric 노트북 안의 실행문이 `System_Cancelled_Session_Statements_Failed`로 실패했다는 것까지는 찾았습니다. 그런데 상태 API와 Spark 로그 어디에도 실제 Python 예외가 없어서, 실행 스냅샷을 열어 실패한 셀의 Traceback을 보내 달라고 했습니다. 제 답은 이랬습니다.

> "확인이 안됩니다. 직접 azure에서 확인해주세요"

## 대응과 결과

**먼저, 비켜 간 답은 원문을 다시 가리켜서 돌려놓았습니다.** 오후 3시 49분에 이렇게 썼습니다.

> "@ko-origin.md 가 해야할 프로젝트고 5개의 agent 설명도 간단히 있어요. 다시 분석해주세요"

답의 첫 줄은 "맞습니다. 제가 앞서 원문의 프로젝트를 '심사 보조 MVP'로 지나치게 축소하고, 지정된 5개 에이전트를 다른 역할로 바꿨습니다."였습니다. 그러고는 사례 문서의 전체 여정을 다시 펼쳤습니다. 동의 확보 → 데이터 취합 → 여신 평가 → 사람 승인 → 지속 모니터링 → 필요 시 상환 안내·지원 → 동의 갱신·만료·삭제. 원문의 다섯 역할은 그대로 두고, 각 역할을 얼마나 깊게 구현할지만 조정하자는 쪽으로요.

화면 오해는 한 문장으로 풀렸습니다. "사업자가 신청하는 사업자 포탈 화면을 말한것입니다." 에이전트는 담당자 화면 중심으로 해석했다고 인정하고 답을 다시 썼습니다.

설명이 너무 많았던 건 에이전트가 먼저 짚었습니다. "제가 저장소·API·Durable Functions·LLM을 한꺼번에 설명해서 복잡해졌습니다." 기술 이름을 빼고 상자 네 개로 다시 그렸습니다. 화면, 코드 오케스트레이터 역할의 업무 서버, 5개 업무 담당 프로그램, 저장소. 한 줄짜리 비유도 붙였습니다. 에이전트는 업무 담당자, 오케스트레이터는 진행 관리자, DB는 공동 업무 기록. 이 설명은 번역해 둔 사례 문서 파일에 덧붙여 달라고 했습니다.

**다음으로, 쌓인 노트는 brainstorming으로 spec이 되게 했습니다.** 오후 6시 33분, 묻기에서 만들기로 넘어갔습니다.

> "/superpowers:brainstorming 현재 논의된 내용을 기반으로 간단하게 데모를 local 에 만들어서 테스트 해볼수 있나요?"

이어서 승인 양식이 하나씩 떴습니다. 범위는 5개 역할 전체, 모델은 실제 추론. 그리고 제가 "local 환경이라 github copilot sdk 로 가능할까요?"라고 묻자, 판단이 필요한 세 역할은 GitHub Copilot SDK로 가는 방향을 잡았습니다. 이때 API 키나 토큰은 입력하지 말고 제공자와 모델명만 알려 달라고 분명히 적었습니다. 그다음엔 숫자가 들어간 동작 기준이 나왔습니다. 현재 현금 300만 원, D+3 정산 500만 원, D+5 급여 600만 원, D+10 상환 100만 원. 정산을 D+8로 미루면 D+5의 부족을 경보로 띄운다. 아마 이렇게 숫자로 보여 줘서 "이 범위로" 고르기가 쉬웠던 것 같습니다.

여기서 제가 한 말 두 마디가 남았습니다. 하나는 "superpowers skill 을 이용해서 plan 과 spec 을 만들때는 한글로 만들어 주세요". 적용 범위는 앞으로 모든 프로젝트로 골랐습니다. 다른 하나는, spec은 썼지만 검토가 남았다는 답을 듣고 한 말입니다.

> "이미 승인된거 같은데 그럼 다음단계로 진행되어야 하는거 아닌가요?"

8분 뒤 한국어 설계서와 작업 10개짜리 plan이 커밋됐습니다. 저는 Native 실행과 별도 worktree를 승인했고, SDK 모델 목록에서 `gpt-6.1-sol`을 골랐습니다. 저녁 7시 8분부터 8시 50분 사이에 기능 커밋 10개가 쌓였습니다.

8시 51분에는 새 리뷰어가 브랜치 전체를 받았습니다. 아마 에이전트가 보낸 것 같습니다. 기록에 제가 쓴 적 없는 영어 지시문이 남아 있거든요. Important 첫 번째는 담당자가 승인한 뒤 예전 실패 작업을 재시도하면 신청이 `APPROVED`에서 `AWAITING_REVIEW`로 되돌아간다는 것이었습니다. 9시 18분, 에이전트는 Important 6건을 고쳤고 실제 모델로 돌린 전체 여정을 포함해 테스트가 통과했다고 알려 왔습니다. 마지막으로 서버가 안 떠 있어서 한 번, 모델이 선택되지 않아서 한 번 걸린 뒤, 9시 24분에는 데모가 담당자 검토를 기다리고 있었습니다.

**이제 시도 1입니다. 에이전트가 직접 들어가 봤습니다.** 403 권한 오류가 제 요청 전인 밤 9시 7분에 한 번, 이번에 또 한 번 났지만, 9시 49분에 원인을 들고 왔습니다. 정상 정규화 셀 앞에 기본 안내 주석만 든 빈 SQL 셀이 끼어 있었고, 그게 `PARSE_SYNTAX_ERROR`(SQLSTATE 42601)를 냈다는 것. 그 셀은 Git 배포본에는 없었습니다. 이때까지는 원인만 확인하고 아무것도 바꾸지 않았다고 했습니다. "수정 및 재실행"이라고 하자 10시 11분에 실행이 끝났고, 결과는 승인 권고(`APPROVE`)·담당자 검토 대기였습니다. 밤 10시 41분에 질문을 하나 더 했고, 기록상 시도 1은 거기서 멈춥니다.

돌아보면, 그날 가장 쓸모 있었던 일은 코드가 아니었습니다. 원문, 평가 기준, 요구사항을 한 문서씩 놓고 기본 질문을 던진 일이었습니다. 에이전트가 비켜 갈 때는 말로 다투는 것보다 "이 파일 기준으로 다시 분석해 주세요" 한 줄이 아마 더 빨랐던 것 같습니다.

## 오늘의 교훈

과제 원문을 에이전트가 읽을 수 있는 파일로 두고 기본 질문은 그 파일에 대고 하자. 답이 비켜 가면 "이 파일 기준으로 다시 분석해 주세요"라고 하면 된다.
