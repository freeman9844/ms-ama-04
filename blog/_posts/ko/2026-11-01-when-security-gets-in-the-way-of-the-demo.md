심사역 콘솔의 로그인이 시연을 막았다. 내가 확인하려던 것은 사용자 인증 절차가 아니라 로그인 이후의 심사 흐름이었다. 그래서 인증을 생략할 화면과 그대로 유지할 접근 통제, 시연 뒤 되돌릴 설정을 구분해야 했다.

## 작업 목표

본선의 오전 과제는 심사역 콘솔이었습니다. 심사역이 신청을 검토하고 결정을 내리는 화면이죠. 설계상으로는 꽤 단단하게 막혀 있었습니다. Entra ID 로그인에 app role 세 개(CreditOfficer, CreditManager, Auditor), 그리고 IP 허용 목록까지.

먼저, 에이전트는 계획을 쓰기 전에 사전 조사부터 했습니다. 관리 ID로 로그인을 연결하는 방식 하나는 아직 비공식이고, 클라이언트 시크릿 없이 ID 토큰만으로 로그인하는 방식은 공식 문서화돼 있다고 알려 줬습니다. 저는 승인 양식에서 최소 범위와 ID 토큰 로그인을 골랐습니다. 10시 38분에 계획이 커밋됐는데, 태스크 7개, 테스트 517개 통과, 그리고 CSRF·XSS·"IP fail-closed" 같은 리뷰 포인트가 11개였습니다. 실행 방식은 이 세션에서 바로 진행하고 실제 배포까지 하는 쪽으로 골랐습니다.

11시 32분, 콘솔이 실제 Azure에 올라갔고 smoke 25개 검사를 모두 통과했습니다. 로그인하지 않은 요청이 Entra 로그인 화면으로 넘어가는 것까지 확인했고요. 남은 건 제가 직접 해야 하는 일이었습니다. 브라우저로 열어서 로그인하고, 신청을 넣고, 결정을 내려 보는 것.

## 요청 범위와 수행 절차

문제를 말로 설명하지 않았습니다. 스크린샷을 붙이고 이렇게 물었습니다.

> "로그인을 시도하면 (스크린샷) 화면이 떠요 어떻게 해야 하나요?"

뜬 화면은 관리자 승인 화면이었습니다. 에이전트는 제 계정에 로그인 권한(openid·profile·email)을 직접 부여하고, 범위는 본인 계정 1명이라고 적었습니다. 그리고 확인할 체크리스트 6개를 내밀었고, 저는 승인 양식으로 답했습니다. 로그인은 성공. 역할을 보여 주는 페이지는 `{"detail":"Not Found"}`. 새 신청 제출은 실패였고, 브라우저에는 "이 페이지를 볼 수 있는 사용자 권한이 없습니다"가 떴습니다. 나머지 세 개는 미확인.

## 관찰된 문제

**먼저, 로그인은 풀렸는데 버튼은 여전히 안 눌렸습니다.** 11시 40분에 에이전트가 첫 번째 벽을 설명했습니다. 테넌트가 사용자 본인의 앱 동의를 막고 있고, 제 계정은 읽기 전용 역할이라 관리자 동의도 할 수 없었다는 것. 그래서 Graph API로 직접 권한을 준 건데, 이 조치가 아직 Bicep에 없는 수동 조치라서 재배포 전에 Bicep에 넣고 ledger에 기록하겠다고 분명히 적었습니다. 이제 로그인과 목록 화면은 됐고, 역할도 확인됐습니다. 새 신청 화면은 CreditOfficer 역할이 있어야 열리는데 그게 열렸으니까요.

그런데 제출은 여전히 403이었습니다. POST 요청이 앱 로그에 남지 않았으니 앱 앞단에서 막힌 것이고, 앱이 직접 403을 주면 오류 문구가 담긴 본문이 오는데 제가 본 건 본문 없는 브라우저 기본 오류 화면이었다는 설명이었습니다. 에이전트는 더 파고들려고 브라우저 요청 헤더를 달라고 물어보던 참이었습니다.

저는 그 질문을 취소하고 대신 이렇게 썼습니다.

> "데모 목적이라 easy auth 를 우선 제거하고 테스트 할 수 있게 해주세요"

왜 그랬는지는 기록에 없습니다. 아마 로그인이 잘 되는 걸 증명하는 게 이 데모의 목적은 아니라고 판단했던 것 같습니다.

**다음으로, 시도 3은 통제를 모두 지키다가 오프라인에 머물렀습니다.** 오후 기준으로 21개 작업 중 16개가 끝났는데, 인프라 단계는 보류 중이었습니다. 모델 가용성, 접속 방식, 비용이 다 미정이었거든요. 승인 양식을 몇 번 거치면서 저는 Global 모델 배포를 비교하고, 사설 접속용으로 새 VM + Bastion 비용을 보는 쪽을 골랐습니다. 에이전트는 한국 중부에서 Global 배포를 쓰면 추론의 국내 처리가 보장되지 않는다고 분명히 했습니다. 접속 구성만 시간당 약 $0.40, 확인된 비용 소계는 시간당 약 $2.97, 가상의 24시간이면 $71.36. 이게 전체 견적이 *아니라는* 점도 못 박았고요. 저는 "진행"이라고 답했습니다.

그럼 그다음은요? 18시 26분, 에이전트가 기존 계획이 Bicep을 *작성하는 일*조차 유료 생성 승인 뒤에 두고 있어서 멈춰 있다고 알려 왔습니다. 비용 승인과 로컬 구현을 분리하자고 해서 저는 승인했습니다. 그러자 구현을 맡은 서브에이전트가 NEEDS_CONTEXT로 멈췄습니다. 외부로 나가는 통신 경로부터 정해야 한다는 것. 저는 NAT Gateway + 별도 공인 IP + 기본 차단 NSG를 골랐습니다. 리뷰와 수정을 두 번 더 돈 뒤 인프라 코드는 승인됐는데, 상태 줄은 `local_complete=true; azure_verified=false`였습니다. 다음 작업은 21시 15분에 또 멈췄습니다. API 게이트웨이는 private endpoint가 생긴 뒤에야 공개 접근을 끌 수 있어서, 임시 공개 bootstrap을 허용할지 결정이 필요하다는 이유였습니다. 그날 Azure에 만들어진 리소스는 없었습니다.

**그리고 시도 5는 진짜를 건너뛰었습니다.** 정오 무렵 새로 시작했고, 설계 세션을 거친 뒤 14시 2분에 이렇게 요청했습니다.

> "이걸 기준으로 Mock 데모를 구현해 주세요. 인프라 아키텍처는 다 구현하고 실제 data 는 mock 으로 해주시고 백데이터를 다 수집해서 모아서 작업을 진행하기 보다는 먼저 웹페이지 작성을 해주세요. 웹페이지는 데모 목적이라 좀 더 화려하고 그래픽이 많이 있었으면 합니다. …"

에이전트는 작은 고정 mock 데이터로 어두운 톤의 "Mission Control" 대시보드를 만들었습니다. 16시 31분에 테스트 23개, Chrome 시연 11개를 통과하고 병합됐고, 저녁에는 합성 기업 8곳으로 늘었습니다. 에이전트는 설계를 묻는 단계에서 화면에 "UI 시뮬레이션"과 "Azure 실제 실행"을 분명히 구분하겠다고 했었습니다. 그런데도 19시 2분에 저는 "LLM 이 적용이 된건가요?"라고 물었고, 답은 이랬습니다. "아니요. 현재는 LLM을 호출하지 않는 UI Mock 데모입니다." 아마 화면이 그럴듯해 보여서 직접 확인받고 싶었던 것 같습니다.

## 대응과 결과

다시 본선입니다. 에이전트가 만든 건 "로그인 삭제"가 아니었습니다. 스위치였고, 범위도 좁았습니다.

- azd 환경 변수 `CONSOLE_AUTH_ENABLED=false`로 Easy Auth를 끕니다.
- 이 모드에서는 모든 요청을 고정 데모 심사역(CreditOfficer) 한 명으로 처리하고, 화면 상단에 "데모 모드" 배너를 띄웁니다.
- 로그인이 없어지니 운영자 IP(`<my-ip>`) 허용만 유일한 관문으로 남습니다.

코드는 11시 48분에 커밋됐고 테스트 532개가 통과했습니다. 배포 중간에 에이전트가 제가 보낸 메시지가 자기 쪽에 보이지 않았다며 다시 보내 달라고 하더군요. 그래서 "현재 상태는? background 처리를 기다리면 되나요?"라고 물었습니다. 12시 3분에 결과가 왔습니다. 배포 창 열기 4.0분, 콘솔 배포 4.2분, 배포 창 닫기 4.3분, smoke 25개 점검 2.4분. 일부러 위조한 CSRF 토큰으로 POST도 보내 봤는데, 이번에는 요청이 앱까지 도착했고 앱이 정상적으로 403으로 거부했습니다. 12시 6분, 제 답은 "새 신청을 해봤고 승인으로 했을때 정상적으로 나오는 것으로 보입니다."였습니다.

돌아보면 가장 쓸모 있었던 건 그다음 같습니다. 에이전트가 브랜치를 새 리뷰어에게 넘겼는데, 제가 쓴 적 없는 그 지시문이 데모 모드를 콕 집어 따로 보라고 하고 있었습니다. 스위치를 안 건드리면 Easy Auth가 모든 곳에서 켜져 있는지, 실수로 데모 모드에 들어갈 수는 없는지, 다시 켜면 로그인이 정말 돌아오는지, 그 밖에 열린 채로 실패할 길은 없는지. 결과는 Critical·Important 0건이었습니다. 데모 모드는 정확히 `false`라는 문자열에서만 켜지고, `False`나 `0`이면 로그인이 그대로 유지되며, 모르는 모드 값이면 앱이 아예 시작하지 않습니다. Minor 하나는 데모 역할 설정이 컨테이너에 전달되지 않는다는 것이었는데, 에이전트는 감사자 데모에서 실명이 보이게 된다며 이걸 Important로 올리고 병합 전에 테스트를 먼저 써서 고쳤습니다.

12시 30분에 "현재 상태는?"이라고 묻자, 답 안에 제 생각엔 그날 가장 중요한 한 줄이 들어 있었습니다. Entra 로그인으로 되돌리려면 `azd env set CONSOLE_AUTH_ENABLED true`를 설정한 뒤 `ops window open --acr`과 `close`를 실행하라는 것.

그날 저녁, 동의 단계의 브라우저 확인 중에 범위에 대해 한 번 더 의견을 냈습니다. "정상적으로 보이나, 중간에 동의 철회 시나리오는 불필요해 보입니다." 에이전트는 곧바로 최종 리뷰로 넘어갔고, 이 의견이 어떻게 됐는지는 그날 기록에 나오지 않습니다.

이제 정리해 보면, 세 폴더는 세 가지 다른 선택을 했습니다. 시도 3은 통제를 다 지켰고, 밤까지 Azure에서 돌아가는 게 없었습니다. 시도 5는 화려한 화면이 있었지만 그 뒤에 모델은 없었습니다. 본선은 통제 하나만 정확히 껐고, IP 관문은 남겼고, 그 스위치가 닫힌 쪽으로 실패하는지 리뷰어가 확인했고, 다시 켜는 방법까지 적어 두었습니다. 처음 해 보는 분이라면, 보안 기능이 내 데모를 막는 순간이 꼭 옵니다. 끄는 것 자체는 괜찮을 수 있습니다. 다만 삭제가 아니라 이름이 붙은, 되돌릴 수 있는 스위치로 끄게 하세요.

## 오늘의 교훈

통제를 건드리기 전에 이 데모가 무엇을 증명해야 하는지부터 정하자. 거기에 도움이 안 되는 것만 끄고, 되돌리는 방법은 반드시 적어 둔다.
