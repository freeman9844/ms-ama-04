# 사후 13주 재생 데이터 현실화와 조기경보 원인 분류 설계

- 날짜: 2026-11-11
- 근거: 사용자 요청("사후 13주 재생 데이터를 좀 더 실제 마켓플레이스 셀러 업체에 맞게 데이터를 현실화", "매출 변화가 아니라 고금리 차입만으로 결과가 안좋아지는것이요")
- 결정(사용자 선택): **B** 셀러별로 다른 마켓플레이스 원인 시나리오, **범위 2** 데이터 + 에이전트 원인 분류, **방법 A** 규칙 기반 원인 후보 + 조사 에이전트가 근거와 함께 주원인 선택. 공통 제안(사후 정산 원장 노출·상환액 일치·대출금 입금)은 이견 없이 수용.
- 선행: P9 조기경보 설계, [정산 인사이트](2026-11-10-settlement-insights-officer-checks-design.md)

## 1. 의도

지금 사후 13주 재생의 나쁜 결말은 사실상 **고금리 차입 하나**로 만들어진다. 확인한 수치(gearstore-06): 주간 매출은 기대치 근처(970만/750만/1,160만)인데 2주차부터 `new_debt`가 뜬다. 실제로 잔고를 끌어내리는 것은 1주차 재고 선매입(dailylook 약 1,660만)·매주 외상 잔금·2주 간격 대부 차입이고, 56일까지 40%로 줄어드는 매출 감쇠는 일별 잡음(±18%)에 묻혀 안 보인다. 심사역이 보기에 "왜 나빠졌는가"의 답이 늘 "대부를 썼다"뿐이다.

실제 마켓플레이스 셀러는 **매출·정산이 먼저 흔들리고, 고금리 차입은 그 결과**다. 판매 부진, 쿠팡 정산 보류, 반품 급증, 광고비·수수료 상승처럼 원인이 다르고, 원인에 따라 대응(상환 유예·정산 연동·광고 조정)도 달라진다. 이 재생을 원인이 다른 네 셀러의 이야기로 바꾸고, 조기경보 에이전트가 **원인을 근거와 함께 짚도록** 한다.

## 2. 목표·비목표·반목표

**목표**
- 네 셀러가 서로 다른 원인으로 악화된다. 각 이야기는 **주문·정산 변화가 먼저 보이고**, 차입은 5~6주차 이후 결과로만 나온다(차입이 없는 셀러도 있다).
- 사후 기간의 **PG 정산 원장**(주문액·반품·보류·공제·지급액)을 만들고 API로 노출한다. 계좌 입금은 심사 때처럼 원장과 시점·상계가 어긋난다.
- 재생 상환액이 실제 대출 원리금과 같다. 대출금 입금이 1일차에 보인다.
- 결정적 탐지기가 원인 후보(정산 보류·반품 급증·비용 증가)를 근거 ID와 함께 낸다. 조사 에이전트는 정산 원장을 조회하고 **주원인 1개 + 부원인 0~2개**를 고르며, 주원인은 해당 원인의 지표를 인용해야 한다.
- 경보 카드에 원인이 보이고, 평가가 시나리오별 **원인 정확도**를 잰다.

**비목표**
- 나머지 17개 셀러의 시나리오 추가(모두 STABLE 유지).
- 심사 단계 데이터·정책 변경(심사 기간 원장·R1xx 규칙은 그대로).
- 추심(Collections)·재조정(Restructure) 에이전트의 판단 로직 재설계. 원인 값은 전달만 한다(§7.4).
- Fabric 등 데이터 플랫폼 변경, 실제 마켓플레이스 API 연동.
- 이미 저장된 재생·경보의 재계산(배포 뒤 새로 시작하는 재생부터).

**반목표(돌아가도 실패)**
- 매출·정산 변화 없이 차입만으로 결말이 나빠진다.
- 정상(STABLE) 셀러에게 새 탐지기 때문에 경보가 뜬다.
- 원인이 근거 지표 없이 붙거나, 차입보다 앞선 변화가 있는데도 "고금리 차입"이 주원인이 된다.
- 콘솔이 원인·지표를 다시 계산한다(값은 오케스트레이터가 저장한 경보·주간 행에서만 나온다).

## 5. Mock API 데이터

### 5.1 시나리오 엔진 (`src/mockapis/postloan.py`)
- `FlowScenario`에 `SALES_SLUMP`, `SETTLEMENT_HOLD`, `RETURN_SPIKE`, `COST_SURGE` 추가. 기존 `STACKING`은 `SALES_SLUMP`로 대체(이름 정리 방법은 빌더 판단, 저장된 재생 JSON 호환만 지킨다).
- 시나리오 매핑은 `demo.py`의 `STACKING_APPLICANTS` 집합 대신 `applicant_id → FlowScenario` 사전.
- 시나리오는 특정 셀러 하드코딩이 아니라 **어느 SyntheticCase에도 적용 가능**하게 만든다(평가가 합성 아키타입에 쓴다). 정산 보류는 쿠팡 채널이 없으면 비중이 가장 큰 오픈마켓 채널에 건다.
- 정답 메타데이터를 `PostLoanFlow`에 추가: `cause`(주원인), `secondary_causes`, `onset`(원인 시작일), `default_on`(없으면 None). 기존처럼 평가 전용, API 비노출.
- 주문 감소는 잡음에 묻히지 않도록 주 단위로 분명해야 한다: 시나리오 셀러는 3주 이동평균 주문액이 원인 주차에 정상 대비 목표치(예: 매출 부진 5주차 ≤ 70%)에 닿는다(테스트로 고정).

### 5.2 사후 PG 정산 원장
- 사후 기간도 `simulate(..., receipt_rng=...)`를 써서 원장(`Ledger.pg_settlements`)과 계좌 입금을 분리한다(시점 차이·광고비 상계·선정산 양도는 기존 `receipts.bank_receipts`).
- 원장 행에 원인 정보를 담는다(내 판단): `PgSettlement`에 선택 필드 `held_krw`(보류액)와 `released_krw`(보류 해제액)를 기본값 0(둘 다 ≥0)으로 추가하고 불변식을 `net_krw = gross - fee - deduction - held + released`로 넓힌다. 기존 JSON은 0이라 호환된다. `gross_krw`의 뜻(반품 차감 뒤 정산 대상액)은 바꾸지 않는다.
- 보류 방식(내 판단): **지급 예정일이 보류 구간(3~6주차)에 든 쿠팡 지급분**을 보류한다(셀러가 실제로 겪는 모습: 받을 날 돈이 안 들어온다). 해당 행은 `held = 정산액`, `net = 0`. 해제일에 같은 플랫폼 행 하나(gross·fee·deduction 0, `released = 누적 보류액`, 적요 "쿠팡(주) 보류 해제")로 일괄 지급한다.
- 반품 급증은 `channels.payouts`의 반품률을 시나리오 구간에서 바꿔 만들고, 반품 회수 택배비는 비용 이벤트로 추가.

### 5.2a 주문일 기준 판매 데이터(내 판단)
정산은 지급일 기준이라 쿠팡처럼 15영업일~2개월 늦게 들어오면 주문 하락이 몇 주 늦게 보인다. "주문·정산 변화가 먼저 보인다"를 지키려고, 셀러센터 판매 리포트에 해당하는 **주문일 기준 일별 판매**(플랫폼·주문일·주문액·반품액)를 원장과 함께 낸다. 판매 부진과 반품률은 이 주문 데이터로 보고, 보류·공제는 정산 원장으로 본다.
- 비용 증가는 광고비 이벤트 배율·`OFFSET_RATE` 상향·택배비 단가 상향으로 만든다.

### 5.3 API
- 새 엔드포인트 `GET /pg/flow?start&end`(PG 동의 범위, `/mydata/flow`와 같은 형태)로 `{settlements, orders}`를 준다. 범위는 **대출 전 8주 + 사후 13주**(대출 전 구간은 기준선용, §6). 기존 `/pg/settlements`(심사 기간)는 그대로.
- 오케스트레이터 `MONITORING_SCOPES`에 `"pg"` 추가.
- PG 데이터를 못 받으면(동의 실패·호출 실패) 재생은 멈추지 않고 계좌 데이터만으로 진행한다: 원장 필드는 비고, 원장 도구는 "데이터 없음"을 돌려주고, 보류·반품·비용 후보는 나오지 않는다(내 판단).

### 5.4 상환액 일치와 대출금 입금
- 지금은 재생 상환액이 287,000원 고정이라 실제 원장(예: 852,885원)과 다르다. 재생 시작 때 오케스트레이터가 `amount_krw`·`tenor_months`(또는 월 상환액)를 `/mydata/flow`와 `/pg/flow`에 넘기고, Mock은 그 값으로 흐름을 만든다(사전 생성 캐시는 (applicant, 상환액) 키, 결정론 유지).
- 1일차에 "에이엠에이렌딩 대출금" 입금, 같은 주에 자금용도대로 약 90%를 재고·운영비로 지출(내 판단: 버퍼가 부풀어 STABLE의 buffer 지표가 왜곡되지 않게).
- 상환액이 커지면 시나리오 부도일·미납 시점이 달라지므로 `_capex_plan`류 조정은 실제 상환액을 넣은 뒤 계산한다.
- 하위 호환: 금액 인자가 없으면 지금처럼 287,000원·대출금 입금 없음으로 만든다(배포 순서: Mock API → 오케스트레이터 → 콘솔).

### 5.5 선정산의 사후 처리(내 판단)
- 심사 때 이미 선정산을 쓰던 셀러(mugshop-21)는 사후에도 같은 양도가 이어진다(현실적). 이것은 기준선에 있는 기존 자금 조달이라 `new_debt`·고금리 차입으로 세지 않는다.
- 사후에 **처음** 나타나는 선정산(gearstore 4주차)은 "신규 선정산" 신호로 기록하되 고금리 차입이 아니라 정산 보류의 부원인 근거로 쓴다. 원인 enum에 따로 넣지 않는다.

## 6. 탐지기와 지표 (`src/agents/monitoring.py`)

- 주간 행에 원장 집계 필드 추가: 주문 데이터에서 `order_gross`, `returns`, `return_rate`(주문일 기준), 정산 원장에서 `held`, `deductions`, `deduction_rate`, `settle_net`(지급일 기준). 근거 ID는 기존 `W:{n}:{field}` 형식.
- 원장 기준선(정상 주문액·반품률·공제율·광고·물류 출금)은 저장된 `Baseline`을 고치지 않고 **재생 시작 때 `/pg/flow`의 대출 전 8주**로 결정적으로 계산해 재생 문서에 둔다(내 판단). 그래서 이미 있는 대출도 새 대출 없이 바로 새 재생을 돌릴 수 있다. 원장이 없으면 원장 기준선도 없다.
- 새 트리거(원인 후보):
  - `settlement_hold`: 주간 보류액 ≥ 기대 주간 정산의 30% (또는 한 플랫폼 지급이 2주 연속 0이면서 그 플랫폼 주문은 정상)
  - `return_spike`: 2주 연속 반품률 ≥ 기준선의 2배 이고 +5%p 이상
  - `cost_surge`: 2주 연속 공제율이 기준선 +4%p 이상, 또는 광고·물류 출금이 기준선 1.5배 이상
  - 기존 `inflow_drop`(계좌 입금 기준)은 그대로 두고, **주문액 기준 판매 부진**(`sales_slump`)을 따로 둔다: 3주 주문액이 원장 기준선(대출 전 8주 주평균) 대비 0.75 미만
  - 수치는 시작값이다. 확정 조건(내 판단): **새 트리거 4개**는 모든 STABLE 셀러(데모 21개 중 17개)와 평가 STABLE 경로에서 발화 0. 기존 트리거는 지금처럼 STABLE에서도 발화할 수 있고(에이전트가 걸러 냄), 에이전트 경보 기준의 오탐은 평가의 `ew_false_alarm`으로 본다.
- 결정적 **원인 후보** 함수: 발화한 트리거를 원인 enum으로 매핑하고, 각 후보에 첫 발화 주차와 근거 ID를 붙인다. `new_debt`는 `high_cost_borrowing` 후보이며 다른 후보보다 늦게 나타나면 "결과"로 표시한다.

## 7. 조기경보 에이전트

### 7.1 계약 (`shared/contracts.py`)
- `AlertCause` StrEnum: `sales_slump`(매출 부진), `settlement_hold`(정산 보류), `return_spike`(반품 급증), `cost_surge`(비용 증가), `high_cost_borrowing`(고금리 차입).
- `EarlyWarningAlert`에 `primary_cause: AlertCause | None = None`, `secondary_causes: tuple[AlertCause, ...] = ()`. 옛 경보는 None.
- `SignalKind`에 `settlement_hold`, `return_spike`, `cost_surge` 추가.

### 7.2 도구와 지시문 (`src/agents/early_warning.py`)
- 새 도구 `get_settlement_ledger(from_week, to_week)`: 플랫폼별·주별 집계(주문액·반품·보류·공제·지급). 개별 원장 행은 주지 않는다.
- 컨텍스트에 원인 후보 목록(원인·첫 주차·근거 ID)을 준다. `raise_alert`에 `primary_cause`, `secondary_causes` 인자.
- 지시문 추가: "차입은 대개 결과다. 차입보다 앞선 주문·정산·반품·비용 변화가 있으면 그것을 주원인으로 고른다."
- 근거 검증(`check_alert`): 주원인의 신호 중 하나는 그 원인의 지표 군(예: 정산 보류 → `W:n:held`)을 인용해야 한다. 후보에 없는 원인을 주원인으로 고르면 거부하고 재시도(기존 재시도 경로).
- `fallback_alert`: 가장 먼저 발화한 후보를 주원인으로.
- 경보가 여러 번 나면 매번 그때까지의 전체 데이터로 원인을 다시 고른다(뒤 경보가 주원인을 바꿀 수 있다). 시나리오는 정답 원인이 **가장 먼저** 발화하도록 설계한다.

### 7.3 콘솔
경보 카드 머리에 원인 칩, 모니터링 탭에 주간 정산 원장 표를 추가한다.

```
 - 쿠팡 지급 2주 연속 0원, 보류 1,240만 원 (W:3:held, W:4:held)
 - 5주차 대부 입금 150만 원 (W:5:loan_proceeds)
 권고: 차주 연락

주간 정산(PG 원장)
 주차 | 주문액 | 반품 | 보류 | 공제 | 지급
  3   | 9.8M  | 0.4M | 4.1M | 0.9M | 4.4M
```
옛 경보는 원인 칩 대신 "—". 라벨은 `src/console/monitoring.py`에 둔다.

### 7.4 추심·재조정 연결
알림 문서에 원인이 저장되므로 추심 에이전트 입력에도 그대로 실린다. 추심 지시문의 상환 유예 대상 신호에 `settlement_hold`·`return_spike`를 추가(한 문장). 판단 로직 재설계는 비목표.

## 8. 평가 (`src/evals`)

- 경로: 4개 원인 시나리오 × 합성 아키타입 + STABLE. 경로 수는 지금(6개) 대비 크게 늘리지 않는다(빌더 판단, 대략 8~10개).
- 성공 기준: 원인 시나리오는 **원인 시작 후 3주 안** 경보(부도 여부와 무관), STABLE은 경보 없음. 실패 코드에 `ew_wrong_cause` 추가.
- 지표: 탐지율, 오탐률, 원인 정확도, 부도 경로만 사전 감지 일수(기존 lead_days), detector_only 기준선의 원인 정확도(후보 중 첫 발화).
- 원인 정확도 채점(내 판단): 경로의 **첫 경보** 주원인이 정답과 같으면 정답. 심사역이 처음 받는 판단이 맞아야 하기 때문이다. 마지막 경보 주원인 일치율은 참고 지표로 함께 낸다.
- `ops eval` 실행은 사용자 승인 뒤에만.
