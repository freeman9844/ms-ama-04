# 콘솔 비주얼 리디자인(B안 · 핀테크 앱형) 설계

- 날짜: 2026-11-18
- 상태: 승인 대기
- 규모: 작은 변경(스타일 한 파일 재작성 + 템플릿 5개 + 상태 값 1개). 짧은 설계 문서로 진행한다.
- 승인 시안: `.superpowers/brainstorm/735-1794975495/content/design-b-v1.html`(git 미추적, 참고용)

## 의도와 이유

데모를 **실제 서비스처럼 보이게** 하려는 변경이다. 지금 화면은 Azure 포털 풍의 차분한 업무용 디자인(그라데이션 0, 그림자 3곳)이라 시제품처럼 보인다. 고객 콘솔은 토스·카카오뱅크 같은 금융 앱처럼, 심사 콘솔은 같은 톤의 모던 업무용 SaaS처럼 보이게 한다.

## 목표 / 비목표 / 반목표

- 목표
  - 고객·심사 콘솔 모두 B안 톤(밝은 회청색 배경, 둥근 카드, 옅은 그림자, 파랑→보라 강조, 색 알약 배지, 그라데이션 로고).
  - 고객 신청 진행 현황에 큰 금액 카드 + 4단계 진행 표시.
  - 고객 사업자 선택을 아바타 카드 격자로.
  - 심사 홈 지표 카드에 색 아이콘 칩.
- 비목표
  - 신청 상세(`detail.html`)·대출 화면(`loan.html`)·운영 지표(`ops.html`)의 구조 변경. 이들은 공통 CSS 효과만 받는다.
  - 다크 모드, 웹 폰트, 차트 라이브러리 도입, 메뉴 구조 변경.
- 반목표(동작하더라도 실패로 본다)
  - CSP 완화(`style-src 'self'` 유지, 인라인 `style` 속성·`<style>` 블록 금지).
  - 기존 클래스 이름 삭제·변경으로 테스트나 `mt.js`·`tabs.js` 등 스크립트가 깨지는 것.
  - 장식 때문에 긴 문서(평가서·정책 근거·표)의 가독성이 떨어지는 것. 본문 대비는 WCAG AA(4.5:1) 이상.
  - 색만으로 상태를 구분하는 것(배지·단계는 항상 글자 동반).

## 접근 방식(검토한 안)

| 안 | 내용 | 결과 |
|---|---|---|
| 1. CSS만 다시 칠하기 | `console.css`만 교체 | 큰 금액 카드·단계 표시 불가라 B안 느낌이 약함 |
| **2. CSS + 핵심 화면 몇 곳(선택)** | CSS 재작성 + 고객 화면 템플릿 소폭 수정 + 로고 | 노력 대비 효과가 가장 큼. 사용자 선택 |
| 3. 전면 재설계 | 상단 메뉴·모바일 우선·대시보드 재배치 | 28KB 템플릿까지 건드려 위험·작업량 과다 |

디자인 방향도 A(Azure 포털 강화)·B(핀테크 앱)·C(다크 글래스) 중 사용자가 B를 골랐다.

## 결정된 내용

### 공통(`src/console/static/console.css`)
- 토큰 교체: 배경 `#f6f8fc`, 카드 `#fff`, 본문 `#191f28`, 보조 `#8b95a1`, 강조 `#3182f6`→`#7c5cff` 그라데이션, 상태색 파랑 `#3182f6`·초록 `#22c55e`·주황 `#f59e0b`·빨강 `#f04452`·보라 `#7c5cff`. 배지 글자색은 AA를 만족하는 진한 톤(예: 초록 배지 `#12873f` on `#e7f8ee`).
- 카드 반경 14px(히어로 18px), 그림자 `0 4px 14px rgba(0,0,0,.05)`, 버튼 반경 10px.
- 상태 배지(`.status`, `.pill`, `.badge-*`, `.apply-status`)는 알약 모양 + 새 팔레트. 기존 클래스 이름은 유지한다.
- 차트(서버 SVG)는 구조 그대로, 색 토큰만 새 팔레트로 바뀐다.
- 로고: 그라데이션 둥근 사각형 안의 "A". 인라인 SVG(`<svg>` 요소)라 CSP와 무관하다.

### 심사 콘솔
- 사이드바는 남색 유지 + 세로 그라데이션(`#14213f`→`#1e2f57`), 활성 메뉴는 둥근 반투명 알약.
- 지표 카드(`.kpi.kpi-<tone>`)에 CSS `::before` 아이콘 칩(톤별 색). 템플릿·매크로 변경 없음.

### 고객 콘솔
- 사이드바를 흰 배경 + 파랑 알약 활성 표시로(`.customer-shell` 범위).
- **진행 단계:** `CustomerStatus`에 `step: int`(0~3)를 더한다. 단계 이름은 `접수`·`데이터 심사`·`심사역 검토`·`결과`.
  - 문서 없음(접수 대기) → 0, `_REVIEWING`(및 `status` 없음) → 1, `_OFFICER` → 2, 승인·거절·철회·종료 → 3.
  - 현재 단계에 `aria-current="step"`, 지난 단계는 완료 표시. 결과 단계 색은 기존 `tone`(good/bad)을 따른다.
- **신청 진행 현황(`apply_status.html`):** 히어로 카드에 사업자·신청번호, 큰 금액(승인 금액이 있으면 승인 금액, 없으면 신청 금액), 기간(개월), 단계 표시, 상태 배지 + 안내 문구. 라우트가 문서의 `requested_amount_krw`·`requested_tenor_months`를 넘긴다(문서가 없으면 생략).
- **신청 현황(`borrower.html`):** 최신 신청 1건을 같은 히어로 카드로 위에 보여 주고, 아래 표는 그대로 둔다.
- **사업자 선택(`customer_select.html`):** 목록 대신 카드 격자. 카드마다 이름 첫 글자 아바타, 색은 순서대로 `av-1`~`av-6` 클래스.

### i18n
- 새 문구(`접수`·`데이터 심사`·`심사역 검토`·`결과` 등)는 `locales/en/customer.json`에 영어를 넣는다. 다른 카탈로그와 같은 키가 다른 번역이면 `load_catalog`가 실패하므로 충돌을 확인한다.

### 문서
- `console.css` 머리 주석의 "Azure Portal 풍(P7)" 설명과, 화면 모양을 설명하는 리빙 문서(예: `docs/architecture.md`, `docs/demo/demo-script.md`)를 새 디자인에 맞춘다.

## 제약

- CSP `style-src 'self'`, `img-src 'self' data:` 그대로. 외부 폰트·CDN 금지.
- 기존 테스트의 클래스 단언(약 56곳)이 계속 통과해야 한다. 새 클래스는 더하기만 한다.
- 배포는 콘솔만(`ops deploy console`). 오케스트레이터 변경 없음.

## 빌더에게 맡기는 것

- 정확한 간격·글자 크기·그림자 수치, 아이콘 글리프 선택, 좁은 화면(약 720px 이하)에서 사이드바를 위로 쌓는 반응형 처리 여부(내 제안: 넣는다).
- 히어로 카드·단계 표시의 마크업 세부와 클래스 이름(기존 이름과 겹치지 않게).
- 진행 단계 계산을 템플릿이 아니라 `customer.py`에 두고 단위 테스트로 고정하는 방식.
