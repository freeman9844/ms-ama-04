# 영문 화면 사전 번역(영구 저장 + 생성 시 번역) 설계

- 날짜: 2026-11-15
- 상태: 초안(빌더 검토 반영, 사용자 승인 대기)
- 이전 단계: `223962d` 영문 화면 데이터 번역(카탈로그 + 브라우저 요청 기계 번역), `6e9f67e` WAF 제외

## 1. 의도와 이유

영문 화면에서 에이전트 의견·경보 요약·추심 문구 같은 데이터 문구는 지금 페이지가 뜬 뒤 브라우저가 `/i18n/translate`로 번역을 받아 바꾼다. 라이브에서 첫 표시가 9~30초 늦었고, 결과는 콘솔 레플리카 메모리에만 있어 재시작·다른 레플리카에서는 다시 번역한다. 데모(영문 화면 시연)에서 처음 여는 화면부터 바로 영어로 보이는 것이 목적이다. 사용자는 "영구 저장 + 생성 시 미리 번역"(①+②)과 그 구현으로 "Cosmos 변경 피드 트리거 + `translations` 컨테이너"(A)를 골랐다.

**성공 기준:** 신청·대출이 만들어지고 수십 초가 지나면 영문 상세·대출·이의 화면이 처음 열 때부터 영어로 렌더되고(기계 번역 표시 유지), 브라우저 번역 요청이 0건이다. 콘솔을 재시작해도 같다.

## 2. 목표 · 비목표 · 반목표

- **목표**
  - 번역 모델에는 가명 처리한 문구만 보낸다. 이미 배포한 즉시 번역 경로도 같이 고친다(5.0).
  - 오케스트레이터 쪽 함수가 문서 변경을 받아 새 데이터 문구만 번역해 Cosmos `translations`에 저장한다.
  - 콘솔이 렌더 시 저장된 번역을 먼저 써서 서버에서 영어로 그린다.
  - 기존 데이터도 한 번 자동으로 번역된다(백필).
- **비목표**
  - 콘솔의 즉시 번역(`/i18n/translate`) 결과를 Cosmos에 저장하지 않는다(콘솔은 읽기 전용 유지). 저장 번역이 없는 문구는 지금처럼 브라우저 번역 + 메모리 캐시로 처리한다.
  - 에이전트가 처음부터 영어를 함께 쓰게 바꾸지 않는다(평가된 지침·출력 스키마를 건드리지 않는다).
  - 번역 품질 평가 suite는 만들지 않는다.
- **반목표(기술적으로 돌아가도 실패로 본다)**
  - 실명·사업자번호·대표자명·거래 원문 같은 식별 정보가 번역 모델로 가는 것.
  - 심사·사후 흐름에 지연·실패가 생기는 것(번역은 흐름 밖에서만).
  - 콘솔에 Cosmos 쓰기 권한을 주는 것.
  - 번역문이 원문 대신 감사·근거 기준이 되는 것.

## 3. 제약

- 콘솔 관리 ID는 Cosmos Data Reader(데이터베이스 범위), 오케스트레이터는 Data Contributor(데이터베이스 범위)다(`infra/resources.bicep:286-290`). 새 컨테이너도 이 범위에 들어간다.
- Functions는 Flex Consumption(FC1)·Python 3.12·v2 프로그래밍 모델(`src/orchestrator/function_app.py`), VNet 통합·Cosmos 개인 엔드포인트 안에 있다.
- LLM 호출은 AI 게이트웨이를 거친다. 번역 연결은 `gw-translator`(50K TPM, 콘솔 즉시 번역과 공유), 모델 `gpt-6-luna`.
- `loan_id`는 신청 ID와 같다(`src/orchestrator/journey/activities.py:418`). 이의(grievances)는 `application_id`로 분할된다.
- 동의 철회 후에도 신청 기록은 보존 대상이다(`consent.py`의 `retained`). 번역은 보존되는 기록에서 파생되므로 같은 기준을 따른다.
- 데이터 문구 렌더 지점은 템플릿의 `|mt`·`|mt_ref` 필터다(`src/console/translate.py`).

## 4. 접근 방식(검토한 것)

| 방식 | 내용 | 장점 | 단점 | 결정 |
|---|---|---|---|---|
| A. 변경 피드 트리거 + `translations` | Functions에 Cosmos 트리거 함수 추가, 새 문구만 번역해 별도 컨테이너에 저장 | 흐름과 분리, 백필 자동(리스 처음부터), 원 문서 충돌 없음 | 저장 후 수 초~수십 초 지연, 리스 컨테이너 필요 | **선택** |
| B. 저장 단계 동기 번역 | 활동이 저장할 때 같이 번역 | 단순 | 단계마다 5~30초 지연, 수정 지점 많음, 백필 별도 | 기각(반목표: 흐름 지연) |
| C. 원 문서 안에 저장 | 원 문서에 `i18n_en` 필드 | 컨테이너 불필요 | `update_doc` 조건부 교체와 충돌, 문서 비대 | 기각 |

사용자가 ①+②, 그리고 A를 골랐다.

## 5. 설계

### 5.0 가명 처리 원칙(이미 배포한 경로 수정 포함)

- 확인한 사실: 심사역·여신 관리자(`can_restore`)는 저장된 가명 토큰(`[[BIZ_…]]` 등)을 실명으로 복원한 문구를 본다(`src/console/views.py:56-66`, `monitoring.py`). 지금의 `|mt`는 이 복원된 문구를 그대로 `/i18n/translate`로 보내므로 실명이 번역 모델로 갈 수 있다. 사람이 쓴 문구(이의 내용, 심사역 사유, 심사역이 고친 발송 문구, 재조정 메모)는 처음부터 가명 처리되지 않았다.
- 규칙: **번역 단위는 "가명 처리한 문구"다.** 번역하기 전에 그 건의 가명처리기(`build_pseudonymizer`: 알려진 상호·대표자·사업자번호·적요 이름 + 패턴)로 마스킹한다. 원천 데이터가 없으면(동의 삭제 등) 패턴 마스킹(`find_pii` 패턴)만 한다. 번역 모델은 토큰을 그대로 둔다(기존 지침).
- 표시: 영어 결과에 토큰이 있으면 복원 권한자에게는 실명으로 복원하고(상호는 카탈로그 영문이 있으면 영문), 감사자에게는 토큰 그대로 보인다(기존 한국어 화면과 같은 규칙). 결과에서 원문의 토큰이 빠지거나 바뀌면 그 번역은 버리고 원문을 둔다.
- 저장 키: `translations.id`는 마스킹한 문구의 sha256이다. 콘솔은 화면 문구를 같은 방식으로 마스킹해 조회한다.
- 즉시 번역 경로: `data-mt`에는 마스킹한 문구를 싣고, `/i18n/translate`가 돌려준 영어를 서버가 복원해 준다. 이를 위해 요청에 owner(신청 ID)를 함께 보내고, 서버는 그 건의 가명처리기로 복원한다(권한 확인 포함).

### 5.1 번역 대상 정의(공유 모듈)

- 컨테이너별 **허용 목록**(문서 경로)을 한 모듈에 둔다. 예: `applications`의 의견 주장·요약·신호·확인 사항·반사실 설명·검토 지적·심사역 결정 사유, `alerts`의 경보 요약·확인 조치·추심 제안 사유·발송 문구, `loans`의 재조정·플랜 변경 사유·메모, `grievances`의 이의 내용·회신 본문·제목·결정 사유.
- 허용 목록 밖은 보내지 않는다. 허용 목록은 범위를 정하고, 식별 정보 차단은 5.0의 마스킹이 맡는다. 한국어가 없는 문자열·카탈로그(`data.json`) 적중은 건너뛴다.
- 콘솔(`console`)과 Functions(`orchestrator`)가 같은 모듈을 쓴다. 두 이미지에 모두 들어가는 패키지(`agents` 등)에 둔다.
- **커버리지 시험:** 미리보기 픽스처로 렌더한 영문 페이지의 모든 `data-mt` 문구가 허용 목록 추출 결과에 들어 있어야 한다.

### 5.2 `translations` 컨테이너

- 파티션 키 `/owner_id`(= 신청 ID = 대출 ID). 문서 하나 = 문구 하나.
- 필드: `id`(원문 sha256), `owner_id`, `source`(컨테이너), `en`, `model`, `translated_at`. 원문은 다시 저장하지 않는다(원 문서에 있다).
- 리스 컨테이너 `leases`(파티션 키 `/id`)를 함께 만든다.

### 5.3 변경 피드 함수

- `applications`·`loans`·`alerts`·`grievances` 각각에 Cosmos 트리거(같은 리스 컨테이너, 리스 접두사 구분, 관리 ID 연결).
- 처리:
  1. 문서 → 허용 목록 추출 → 5.0 마스킹(원천 Blob에서 가명처리기 생성, 원천이 없으면 패턴만).
  2. owner의 기존 번역 id와 비교해 없는 것만 남긴다.
  3. `Translator`로 25개·8,000자씩 번역한다.
  4. `translations`에 upsert한다.
- 다시 바뀌어도 이미 번역된 문구는 건너뛰므로 반복 호출 비용이 작다. 원 문서는 쓰지 않는다(트리거 루프 없음).
- 실패(429·차단·기타)는 로그만 남기고 그 문구를 건너뛴다. 콘솔 즉시 번역이 대신한다. 429는 재시도 정책(지수 백오프)으로 몇 번 다시 시도한다.
- 백필 범위: eval·load·smoke가 같은 컨테이너에 합성 신청을 넣으므로 처음부터 전체를 읽지 않는다. 트리거 시작 시점을 배포 7일 전으로 두어 최근 문서만 백필한다. 이후 새 문서는 모두 번역한다(건당 비용 1센트 미만). 콘솔 즉시 번역과 50K TPM을 나눠 쓰므로 함수 동시성은 1, 배치 크기는 작게 둔다.
- 로그는 owner·개수·글자 수·토큰 수·결과만 남기고 문구 본문은 남기지 않는다.

### 5.4 콘솔 렌더

- 조회 키는 5.0의 마스킹 문구다(뷰 모델이 복원 전 문구를 함께 넘기거나, 화면 문구를 다시 마스킹한다. 가명처리기는 결정적이라 같은 토큰이 나온다).
- 영문 요청에서 페이지가 owner 문서를 읽을 때 `translations`를 owner 단위 단일 파티션 쿼리로 함께 읽어 요청 컨텍스트에 둔다.
- `mt`·`mt_ref` 조회 순서: 카탈로그 → **저장 번역** → 메모리 캐시 → 대기(브라우저 번역).
- 저장 번역 표시는 지금의 기계 번역 표시(점선 밑줄·원문 툴팁, `mt_ref`의 `EN ·`)와 같다.
- 한국어 화면에서는 읽지 않는다.

### 5.5 인프라·설정

- bicep:
  - Cosmos 컨테이너 `translations`·`leases`를 추가한다.
  - Functions 앱 설정에 `TRANSLATE_MODEL`(`gpt-6-luna`)과 Cosmos 트리거 연결 설정(관리 ID, `__accountEndpoint`)을 추가한다.
  - 역할은 기존 데이터베이스 범위 역할로 충분한지 확인한다(트리거는 리스 쓰기가 필요하다. Contributor면 된다).
- 게이트웨이 `CONNECTIONS`의 번역 에이전트 연결(`gw-translator`)을 Functions에서도 쓴다.
- 문서(`agents.md`·`architecture.md`·`limitations.md`·`locales/README.md`·`deploy-history.md`)를 갱신한다.

### 5.6 배포·검증

- `window open --acr` → `ops deploy orchestrator` → `ops deploy console` → `ops smoke`.
- 백필 진행은 로그로 확인하고, 끝난 뒤 `/applications/<id>?lang=en`·`/loans/<id>?lang=en`이 처음부터 영어인지(`data-mt` 대기 0) 확인한다. 이어서 새 신청 1건을 만들어 1분 안에 영어로 렌더되는지 본다.
- `window close`, 푸시는 사용자 승인 뒤에 한다.

- 공유 모듈의 위치·이름, 트리거 함수 이름, 리스 접두사, 배치·동시성 수치, 재시도 횟수.
