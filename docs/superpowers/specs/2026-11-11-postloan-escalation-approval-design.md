# 조기경보 단계별 자동 대응과 추심 심사역 승인 설계

- 날짜: 2026-11-11
- 근거: 사용자 요청(조기경보 = "상환이 어려워질 징후를 미리 발견하는 역할", 추심 = "상환 안내와 어려움을 겪는 고객의 해결 절차를 지원하는 역할")
- 결정(사용자 선택): 셀프 상환 플랜은 **2 실제 변경**(고객 수락 → 심사역 승인 → 상환 일정 변경 → 재생 반영), 구현은 **A 기존 재조정 흐름 확장**, 자동 발송 연락 시간은 **시뮬레이션 시각 기준**(§5)
- 선행: [사후 13주 재생 현실화](2026-11-11-postloan-replay-realism-design.md), P9 조기경보·추심 설계

## 1. 의도

대출 당시 상환능력이 충분했어도 이후 매출·비용·정산이 달라질 수 있다. 조기경보는 동의받은 최신 자금 흐름에서 최초 심사 이후의 변화를 찾아 **이유와 확인할 조치가 담긴 경보**를 내고, 위험이 높아지면 고객에게 **미리** 안내해 미납을 막는다(원문 L4: 자율 경보 생성·발송). 경보가 대출 회수·한도 축소·부도 확정을 하지는 않는다.

추심은 미납이 생긴 뒤 상환 안내와 상환 곤란 고객의 해결 절차를 지원한다. 에이전트는 **무엇을 왜 할지 자세히 제안만** 하고, 실제 발송은 심사역이 승인·수정해야 나간다. 원문 Collections는 L3("공정 추심 규칙 안에서 행동")지만, 고객 접점 문구를 사람이 확인하는 더 보수적인 해석을 택한다(§10에 이유를 남긴다).

지금 구조와 다른 점:
- 지금은 조기경보가 고객에게 연락하지 않는다. 모든 회차에 3일 전 안내만 고정으로 나간다.
- 지금 추심 에이전트는 미납이면 스크립트를 바로 발송하고, 심사역은 재조정 요청만 결정한다.

## 2. 목표·비목표·반목표

**목표**
- 경보마다 "이유" 문장과 "확인할 조치" 문장을 낸다. 예: "정산일이 7일 지연되어 다음 상환일에 현금 부족이 예상됩니다. / 정산 상태와 다른 계좌의 가용자금 확인이 필요합니다." 문장 속 숫자는 근거 지표와 맞아야 한다.
- 관찰 신호 네 가지(아래 표)를 경보 지시문과 문구에 반영한다. 다음 상환일 예상 잔고가 상환액에 못 미치는지 따로 본다.
- 높음 경보 단계에 따라 고객 안내를 **자동 발송**한다(§5). 1단계: 상환일 사전 안내 강화 + 잔고 부족 예상 알림. 2단계: 상환일 이동 제안 + 분할납부 안내 + 셀프 상환 플랜 링크.
- 고객이 차주 화면에서 플랜을 고르면 심사역 승인 뒤 남은 상환 일정이 바뀌고, 재생은 바뀐 일정으로 납부·미납을 판정한다.
- 미납이면 추심 에이전트가 제안서를 만든다. 심사역이 한 화면에서 **제안 조치와 이유 / 판단 근거와 정책 확인 결과 / 고객에게 보낼 정확한 문구**를 보고 승인·수정·반려한다. 승인·수정한 문구만 발송된다.

| 관찰 신호 | 확인할 위험 | 지금 연결되는 원인·트리거 |
|---|---|---|
| 판매대금 입금 감소 | 상환재원 감소 | `sales_slump`·`settlement_hold`·`inflow_drop` |
| 반품·환불 증가 | 예상 정산액 축소 | `return_spike` |
| 광고비·매입비 증가 | 매출이 유지돼도 가용현금 감소 | `cost_surge` |
| 예상 현금잔액 < 예정 상환액 | 가까운 상환일 자금 부족 | 새 트리거 `due_shortfall`(§4.2) |

**비목표**
- 실제 문자·알림톡 발송. 발송은 연락 이력 기록이다(지금과 같다).
- 분할에 따른 이자 재계산, 대출 조건(금리·만기·한도) 변경.
- 실제 급여일 데이터. 셀러에게는 급여일이 없어 "급여일 뒤"를 **주 정산 플랫폼 지급일 뒤**로 바꾼다.
- 탐지기 임계값·셀러 시나리오 데이터 변경. Mock API 변경.
- 통합 승인함 화면(접근 B). 저장된 옛 재생·경보의 재계산.

**반목표(돌아가도 실패)**
- 추심 메시지가 심사역 승인 없이 나간다. 발송 문구가 심사역이 승인·수정한 문구와 한 글자라도 다르다.
- 조기경보가 회수·한도 축소·부도 확정·금리 변경을 하거나 그렇게 읽히는 문구를 보낸다.
- 같은 단계 안내가 한 재생에서 두 번 나간다. 공정 연락 규칙(7일 7회, 08~21시 KST)을 넘겨 발송된다.
- 이미 보여준 주차의 거래·판정이 일정 변경 뒤 바뀐다.
- 고객 문구에 가명 토큰(`[[PERSON_...]]`)이나 압박·위협 표현이 들어간다.

## 3. 접근(선택 완료: A)

| 접근 | 내용 | 판단 |
|---|---|---|
| **A 기존 재조정 흐름 확장** | 단계 판정은 오케스트레이터 정책 규칙, 문구는 사전 승인 템플릿. 추심 제안·플랜 변경 요청을 재조정 요청처럼 문서에 `pending_officer`로 두고 재생을 멈춘다. 결정은 대출 화면 카드에서 한다 | **선택.** 검증된 멈춤·재개 구조를 재사용해 위험이 작다. 발표 중 클릭할 시간을 멈춤이 준다 |
| B 통합 승인함 | 여러 대출의 대기 건을 한 목록에서 처리 | 화면·라우트가 늘고 데모는 한 대출을 따라가 효과가 작다 |
| C 고객 수락 자동 시뮬레이션 | 시나리오 데이터가 수락 여부를 정해 멈춤 없음 | "고객이 직접 고른다"는 장면이 빠진다 |

## 4. 조기경보 경보 문구

### 4.1 이유 + 확인할 조치
- `EarlyWarningAlert`에 `check_action: str | None`(1~200자)을 더한다. `summary`는 이유(위험이 무엇이고 왜인지), `check_action`은 심사역·고객이 확인할 것이다. 옛 경보는 `None`이고 콘솔은 요약만 보인다.
- 에이전트는 `raise_alert`에 `check_action`을 함께 낸다. 숫자 대조(`ungrounded`)를 요약과 같은 방식으로 적용한다. 지시문에 위 신호 표와 예시 문장을 넣는다.
- 폴백 경보는 원인·트리거별 템플릿 문구를 쓴다(숫자 없이). 예: 정산 보류 → "정산 지급이 보류되어 다음 상환일 자금이 부족할 수 있습니다." / "플랫폼 정산 상태와 다른 계좌의 가용자금 확인이 필요합니다."
- 콘솔 경보 카드는 "이유"와 "확인할 조치"를 나란히 보인다.

### 4.2 다음 상환일 예상 잔고(`due_shortfall`)
- 전망(`projection`)이 이미 이번 대출 원리금을 예정 출금에 넣는다. 여기에 다음 미납부 회차의 상환일 `F:n:next_due_on`과 그날 출금 직전 예상 잔고 `F:n:due_balance`를 더한다.
- `due_balance < 상환액`이면 트리거 `due_shortfall`. 문구 근거로 `F:n:due_balance`와 상환액을 인용할 수 있다.
- 일정이 바뀌면(§6) 바뀐 일정으로 계산한다.

## 5. 단계별 자동 대응(L4, 결정적 정책)

판정과 발송은 LLM 없이 오케스트레이터가 한다. 에이전트는 경보 내용(심각도·이유)만 정한다.

| 단계 | 조건 | 자동 발송 | 재생 |
|---|---|---|---|
| 1 | 이 재생에서 **처음** 높음 경보 | (a) 잔고 부족 예상 알림을 즉시, (b) 이후 회차 상환일 **5일 전 추가 안내**(기본 3일 전 안내는 그대로) | 계속 |
| 2 | **직전 경보와 이번 경보가 모두 높음**(사이에 중간·낮음 경보가 있으면 연속 아님) | 상환일 이동 제안 + 분할납부 안내 + 셀프 상환 플랜 링크를 한 메시지로 | `awaiting_customer`로 멈춤(§6.3) |

- 각 단계는 재생마다 한 번만 발송한다. 2단계를 보낸 뒤의 높음 경보는 다시 보내지 않는다.
- 문구는 사전 승인 템플릿(`balance_warning`, `early_reminder`, `self_plan_offer`)이다. 자리표시자는 날짜·금액·링크만 허용하고 개인 식별 정보는 넣지 않는다. 잔고 부족 알림의 금액은 `F:n:due_balance`가 있을 때만 넣는다.
- 모든 발송은 `fair_check`를 거친다. 걸리면 `deferred`로 기록하고 다시 시도하지 않는다(지금 `remind`와 같다). 연락 이력은 기존 `contacts-{replay_id}` 문서에 `by="early_warning"`으로 남긴다.
- **연락 시간 기준(사용자 결정):** 자동 발송(조기경보 단계 안내, 3일·5일 전 안내)은 시뮬레이션 날짜 오전 10시(KST)에 보낸 것으로 보고 시간대를 검사한다. 7일 7회 검사는 그대로다. 심사역이 승인·수정해 보내는 추심 문구는 실제 시각으로 검사한다. 그래서 밤에 데모해도 자동 흐름은 끝까지 가고, 심사역 발송만 21시 이후 `deferred`가 될 수 있다.
- 금지: 회수·한도 축소·부도 확정·금리 변경. 템플릿 카탈로그 밖 문구는 보낼 수 없다.
- 1단계의 "3~5일 전"은 **5일 전 추가 + 3일 전 기존**으로 정했다(설계 판단: 한 회차에 두 번 알려 대비 시간을 준다).

## 6. 셀프 상환 플랜

### 6.1 제안 내용(2단계 발송 때 결정적으로 계산)
대상은 남은 미납부 회차다. 차주 화면에 다음 세 옵션을 날짜·금액과 함께 보인다.
1. **상환일 이동:** 각 회차를 원래 상환일 이후 **주 정산 플랫폼의 첫 지급일 다음 영업일**로 옮긴다(최대 +10일, 13주 범위를 넘으면 원래 날짜). 주 플랫폼은 원장 기준선에서 비중이 가장 큰 플랫폼이고, 지급일은 그 플랫폼의 정산 주기(지금까지 공개된 지급 이력)로 정한다.
2. **분할납부:** 다음 회차를 두 번에 나눈다. 원래 상환일에 50%, 15일 뒤(영업일 보정)에 50%. 총액은 같다.
3. **지금 일정 유지.**

### 6.2 승인과 반영
- 고객 선택 → 대출 문서에 `plan_change`(옵션, 바뀔 일정, `pending_officer`). 유지를 고르면 승인 없이 재개 대기로 간다.
- 심사역이 대출 화면 "상환 플랜 변경 요청" 카드에서 승인·반려(사유)한다. 승인하면 상환 원장 일정이 바뀌고 변경 이력(`plan_history`)이 남는다.
- **재생 반영:** Mock 흐름은 바꾸지 않는다. 오케스트레이터가 아직 공개되지 않은 거래에서 바뀐 회차의 원래 `에이엠에이렌딩 대출상환` 출금을 빼고, 새 날짜·금액의 출금을 넣는다. 출금 직전 잔고가 금액 이상이면 넣고(납부), 모자라면 넣지 않는다(미납). 이후 거래의 잔고를 다시 계산해 별도 흐름 버전으로 저장한다. 공개된 주차는 그대로다.
- 이미 미납으로 판정된(공개된) 회차는 바꿀 수 없다. 대상은 아직 상환일이 오지 않은 회차뿐이다.
- 시나리오의 강제 미납(`force_missed`)은 오케스트레이터가 알 수 없어 옮긴 날짜로 이어지지 않는다. 옮긴 회차는 잔고 규칙만으로 판정한다(설계 판단, `limitations.md`에 적는다).

### 6.3 재생 멈춤
- 2단계 발송 뒤 재생은 `awaiting_customer`. 고객이 고르거나, 심사역이 "고객 응답 없이 계속"을 누르면 다음으로 간다.
- 플랜 변경 요청이 `pending_officer`면 `paused`, 결정 뒤 `awaiting_resume`(지금 재조정과 같다).
- 2단계 안내가 `deferred`면 플랜을 열지 않고 멈추지 않는다. 단계는 쓴 것으로 본다(재발송 없음). 1단계도 `deferred`면 그 단계는 쓴 것으로 본다.
- "고객 응답 없이 계속"을 누르면 제안은 닫힌다(차주 화면에 만료로 보인다).
- 같은 주에 2단계와 미납이 함께 나면 둘 다 기록하고, 재생은 **대기 중인 항목이 모두 끝날 때까지** 멈춘다(멈춤 사유는 목록). 콘솔은 추심 승인 → 고객 응답 → 플랜 변경 승인 → 재조정 결정 순서로 보인다. 재생이 멈춘 동안에는 주차가 진행되지 않으므로 새 경보·미납은 생기지 않는다(설계 판단).

## 7. 추심 제안과 심사역 승인

### 7.1 에이전트
- 발송 도구(`send_script`·`route_hardship`)를 없애고 `propose` 하나로 바꾼다. 인자: `script_id`(카탈로그 안), `hardship`(선택: category·note), `reason`(두 문장 이내). 한 번만 받는다.
- 판단 지시는 지금과 같다: 첫 미납은 `missed_payment`, 누적 미납 2회 이상이거나 최근 경보 원인이 매출 부진·정산 보류·반품 급증·고금리 차입이면 `hardship_offer` + 재조정 상담.
- 폴백: 최근 경보가 높음이면 `hardship_offer`, 아니면 `missed_payment`. 재조정 상담 없음. 폴백 제안도 같은 승인을 거친다.

### 7.2 제안서(추심 건 문서 `proposal`, 결정적으로 조립)
- **제안 조치와 이유:** 보낼 스크립트, 재조정 상담 요청 여부, 에이전트 이유.
- **판단 근거:** 회차·상환일·금액·누적 미납, 최근 경보의 심각도·원인·이유·확인할 조치, 최근 7일 연락 횟수, 조기경보 단계 발송 이력.
- **정책 확인 결과:** 각 항목 통과/불가와 설명. 승인된 스크립트인가 / 연락 시간대(08~21시 KST) / 7일 7회 이내 / 금지 표현 없음 / 가명 토큰 없음 / 재조정 상담 근거(누적 미납·원인) 충족.
- **고객 문구:** 실제로 보낼 전체 문장(템플릿에 회차·금액·상환일을 채운 것). 추심 문구에는 셀프 플랜 링크를 넣지 않는다. 미납 뒤 상환 곤란은 지금처럼 재조정 상담(심사역 결정)으로 간다(설계 판단).

### 7.3 심사역 결정
- 추심 건 상태 `proposal_pending`, 재생 `paused`.
- **승인:** 제안 문구를 그대로 보낸다. 발송 시점 `fair_check`로 `sent`/`deferred`. 연락 이력 `by="officer"`, 심사역 ID 기록. 재조정 상담이 들어 있으면 지금의 재조정 요청(`pending_officer`)을 만들고 재생은 그 결정까지 계속 멈춘다.
- **수정:** 문구를 고쳐 보낸다. 고친 문구는 금지 표현·가명 토큰·길이(300자) 검사를 다시 통과해야 하며, 못 하면 이유를 보이고 보내지 않는다. 재조정 상담 포함 여부도 바꿀 수 있다.
- **반려:** 아무것도 보내지 않는다. 사유 필수. 재개 대기로 간다.
- 결정 메시지는 기존 `restructure-decisions` 큐에 종류 필드를 더해 보낸다(인프라 변경 없음, 설계 판단).

## 8. 콘솔

대출 화면 추심 카드(예시):
```
3회차 미납 추심 — 심사역 승인 대기
[제안 조치와 이유]  미납 안내 + 재조정 상담 요청 · 누적 미납 2회, 최근 경보 원인 정산 보류
[판단 근거]        3회차 2027-02-08 · 1,170,000원 · 최근 경보 높음(정산 보류) · 7일 연락 2회
[정책 확인]        ✔ 승인 스크립트 ✔ 연락 시간 ✔ 7일 7회 ✔ 금지 표현 없음 ✔ 재조정 근거
[고객 문구]        고객님, 이번 상환일에 자동이체가 처리되지 않아 …(전체)
( ) 승인  ( ) 수정 [문구 편집]  ( ) 반려 [사유]      [결정]
```
- 경보 카드: 이유 / 확인할 조치 / 이 경보로 자동 발송된 안내(단계, 상태).
- 재생 멈춤 배너: 이유별 문구(추심 승인 대기, 재조정 결정 대기, 고객 응답 대기, 플랜 변경 승인 대기).
- 차주 화면(`/borrower/{applicant_id}`): "상환 플랜 제안" 섹션에 세 옵션과 바뀔 일정 표, 선택 버튼. 받은 안내 목록.
- CSP: 인라인 스크립트·스타일 없음(지금 규칙).

## 9. 평가·테스트
- 단위: 단계 판정(처음 높음, 연속 높음, 사이 중간이면 초기화, 재발송 없음), 템플릿 채우기, 상환일 이동·분할 계산, 흐름 덧씌우기(공개 주차 불변·잔고 재계산·잔고 부족이면 미납), 제안서 정책 확인, 수정 문구 재검사, 승인 없이 발송 0건.
- 오케스트레이터: 멈춤·재개 상태 전이(`awaiting_customer`, 추심 승인 대기 → 재조정 대기 → 재개 대기).
- 평가(`evals`): 추심 경로가 승인 전 연락을 만들지 않는다. 시나리오별 단계 발송 횟수 기록.
- 데모 목표: 적어도 한 원인 셀러가 미납 전에 2단계에 닿아, 고객 선택 → 심사역 승인 → 바뀐 일정으로 납부·미납이 판정되는 장면. 결과(납부 여부)는 잔고 규칙이 정하며 "이동 덕분에 납부"를 연출하지 않는다. 어느 셀러가 닿는지는 구현 뒤 실측해 보고하고, 닿지 않아도 데이터는 바꾸지 않는다.
