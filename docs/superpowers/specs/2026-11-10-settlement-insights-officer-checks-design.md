# 정산 대사 해설 보강과 에이전트 정산 확인 사항 설계

- 날짜: 2026-11-10
- 근거: 사용자 요청("신청 상세에서 '정산 대사'에 설명을 좀 더 추가해 주시고 에이전트가 분석할 때 이 부분도 추가로 분석해서 제언을 해줄 수 있는 부분", "현금 흐름 이외에 마켓플레이스 정산이 또하나의 중요 포인트")
- 결정(사용자 선택): 아이디어 1~3(화면 해설·새 지표·에이전트 제언)을 먼저 한다. 사후 모니터링 정산 대사(아이디어 4)는 별도. 제언은 방법 B(심사 결과 계약에 확인 사항 필드 신설).
- 선행 설계: [정산 원장 활용과 정책 v3](2026-11-08-settlement-ledger-policy-v3-design.md)

## 1. 의도

온라인 셀러의 매출은 대부분 마켓플레이스 정산으로 들어온다. 정산 원장은 "이미 확정된 미래 현금"이고 이 대출의 상환 재원이다. 지금 상세 화면의 정산 대사 카드는 숫자와 막대만 있어 심사역이 의미를 바로 읽기 어렵고(예: 월별 공제율 막대의 뜻을 사용자가 따로 물었다), 분석가 에이전트는 정산을 R107·R108 사유가 있을 때 반사실 지표로만 주로 쓴다. 정산을 현금흐름과 나란한 심사 축으로 보이게 한다.

## 2. 목표·비목표·반목표

**목표**
- 정산 대사 카드만 읽어도 각 지표의 뜻과 "왜 대출 심사에 중요한지"를 안다.
- 원장에 이미 있는 정보로 결정적 지표 3개를 더 만든다: 선정산 양도 추정, 현금화 일수, 광고비 상계율 추이.
- 분석가가 정산을 근거로 **심사역 확인 사항**(무엇을 확인·요청할지)을 근거 ID와 함께 내고, 검토자가 검증하고, 정산 카드에 보인다.
- 심사 도우미(심사역 채팅)가 새 지표와 확인 사항으로 답할 수 있다.

**비목표**
- 정책 변경(정책 v3 유지, 새 규칙 없음). 선정산 양도는 이미 R108(입금 비율)로 잡힌다.
- 대출 구조·상환 원장·계약 변경(상환일 정렬·정산 연동 상환은 확인 사항 문장으로만 제안 가능).
- 사후 모니터링의 정산 대사, Mock API 데이터 확장(정산 예정금·주문일 필드 등).
- 이미 심사된 신청의 재계산(새 지표·확인 사항은 배포 뒤 새로 평가하는 신청부터).

**반목표(기술적으로 돌아가도 실패)**
- 콘솔이나 에이전트가 정산 값을 다시 계산한다(값은 `pg_ledger` 한 곳에서만 나온다).
- 확인 사항이 근거 없이 승인·거절·금리를 지시한다.
- 미입금 개별 금액이나 선정산업체 이름 같은 원천 세부가 LLM에 간다(집계만 간다).
- 정상 셀러에게 선정산 추정이 붙는다(오탐).

## 3. 접근 방식

| 방법 | 내용 | 트레이드오프 |
|---|---|---|
| A. 정산 근거 주장 모아 보기 | 기존 claims 중 `M:pg_*` 인용 문장을 정산 카드에 표시 | 계약 변경 없음. 권고형 문장은 검토자가 근거 밖 추론으로 걸러 제언이 약함 |
| **B. 확인 사항 필드 신설(선택)** | `CreditAssessment.officer_checks` 추가, 검토자가 따로 검증, 정산 카드에 표시 | 제언이 구조화되고 근거가 강제됨. 계약·검토자·평가·콘솔 수정(A의 약 2배) |
| C. 요약 문장만 | summary에 정산 문장 추가 | 가장 작지만 카드에 아무것도 안 보임 |

사용자는 B를 골랐다. 심사역이 정산 카드에서 바로 "무엇을 확인해야 하는지"를 근거와 함께 보는 것이 요청의 핵심이기 때문이다.

## 4. 설계

### 4.1 결정적 지표 추가(`src/agents/pg_ledger.py`)

`ledger_summary`의 기존 대상 기간·매칭 규칙은 그대로 두고, 매칭 뒤에 아래를 계산해 결과 dict에 추가한다.

**(1) 선정산 양도 추정**
- 미매칭 정산 `s`마다, 아직 쓰이지 않은 계좌 입금 `t` 중 다음을 모두 만족하는 가장 이른 것을 짝짓는다(한 입금은 한 번만).
  - `t.amount_krw > 0`, 플랫폼 정산 입금이 아님(`_platform_of(t) is None`), 정산 매칭에 쓰인 입금이 아님
  - `s.settled_on - 10일 ≤ t.booked_on ≤ s.settled_on`(달력일)
  - `0.75 × s.net_krw ≤ t.amount_krw ≤ 0.95 × s.net_krw`
- 적요 키워드에 의존하지 않는다(실제 선정산업체 이름은 다양하다). 모의 데이터의 선지급은 정산액의 83~87%, 5~7일 전이라 이 창에 들어온다.
- 새 키:
  - `pg_advance_suspected_count`: 선지급 짝이 있는 미매칭 정산 건수
  - `pg_advance_share`: 선지급 짝이 있는 미매칭 실지급액 ÷ 전체 미매칭 실지급액(소수 셋째 자리, 미매칭이 없으면 None)
  - `unmatched[]` 각 항목에 `advance`: `{"booked_on", "amount_krw", "lead_days"}` 또는 None(콘솔 전용, LLM에는 안 감)

**(2) 현금화 일수**
- 플랫폼별 표준 정산 지연(주문일 → 계좌 입금, 달력일) 상수표 `PLATFORM_LAG_DAYS`를 둔다. 값은 `src/mockapis/sellerdata/channels.py`의 정산 일정 문서화 값(2026 공개 기준 근사)에서 유도한다. 대략 스마트스토어 8, 쿠팡 32(주정산 70% 약 25일 + 최종액 30% 약 48일), 11번가 17, 자사몰 3. 정확한 값은 빌더가 일정표로 계산해 주석에 근거를 남긴다.
- `pg_cash_conversion_days` = Σ(플랫폼 정산 총액 비중 × 지연 일수), 소수 첫째 자리. 상수표에 없는 플랫폼은 계산에서 빼고 비중을 다시 정규화한다. 모두 없으면 None.
- 원장에 주문일이 없으므로 "표준 정산 주기 기준 추정"이라고 화면과 도구 설명에 밝힌다.
- `platforms[]` 각 항목에 `lag_days`(None 허용)를 추가한다.

**(3) 광고비 상계율 추이**
- 월별로 수수료율 `fee_rate` = 수수료/총액, 상계율 `offset_rate` = 상계/총액을 나눠 `monthly_take_rate[]` 항목에 추가한다(기존 `rate`는 그대로, 둘의 합).
- `pg_offset_rate_trend_pp` = 상계율의 최근 3개월 평균 − 이전 3개월 평균(%p, 기존 `_trend_pp` 재사용).

**특성·근거 연결(`src/agents/features.py`)**
- signals에 `pg_cash_conversion_days`, `pg_offset_rate_trend_pp`, `pg_advance_share`, `pg_advance_suspected_count`, `pg_unmatched_count`(= `unmatched_count`)를 None이 아닐 때만 넣는다. `build_catalog`가 숫자 signals를 그대로 `M:` 근거 ID로 만든다.
- `CashFlowFeatures`·정책 엔진은 바꾸지 않는다.

### 4.2 심사 결과 계약(`src/shared/contracts.py`)

```python
class OfficerCheck(Contract):
    """분석가가 심사역에게 권하는 확인 사항 1개. 근거 지표 ID가 하나 이상 있어야 한다."""
    text: str = Field(min_length=1, max_length=200)
    metric_ids: tuple[EvidenceId, ...] = Field(min_length=1)
    supported: bool | None = None  # 마지막 라운드 검토자 판정. 검토자 출력이 없으면 None.

class CreditAssessment(Contract):
    ...
    officer_checks: tuple[OfficerCheck, ...] = Field(default=(), max_length=3)
```

기본값이 빈 튜플이라 기존 문서가 그대로 유효하다. `schema_version`은 "1" 유지.

### 4.3 분석가·검토자(`src/agents/underwriting.py`)

**분석가 출력 스키마:** `ANALYST_OUTPUT_SCHEMA`에 `officer_checks`(배열, 항목 `{text, metric_ids}`)를 추가하고 strict 규칙대로 `required`에 넣는다. `AnalystDraft.officer_checks: list[DraftCheck]`. 근거 ID가 txn_ids 쪽에 섞이는 문제는 없다(필드가 metric_ids뿐).

**지시문(`ANALYST_INSTRUCTIONS`):**
- 1단계의 정산 문장을 넓힌다: 대사율·채널 집중·공제율 추이에 더해 현금화 일수·광고비 상계율 추이·선정산 추정을 확인한다.
- 새 단계: "정산 자료가 있으면 officer_checks에 심사역이 확인할 사항을 0~3개 쓴다. 각 항목은 '무엇을 확인·요청할지 + 이유'를 한 문장으로 쓰고, 이유가 되는 M:pg_* 또는 P:R107·P:R108 근거를 1개 이상 단다. 승인·거절·금리·한도를 지시하지 않는다. 대출 구조 아이디어(예: 상환일을 주력 채널 정산일 직후로)는 '검토'를 권하는 형태로만 쓴다. 정산 자료가 없으면 빈 배열." 예시 1~2개(선정산 계약서 확인, 정산계좌 변경 여부 확인)를 넣는다.
- summary 순서에 "정산 건전성"을 (2) 위험 요인 다음 항목으로 추가하고 문장 수를 6~8로 늘린다. 정산 자료가 없으면 이 항목은 "정산 자료 없음" 한 문장으로 한다.

**도구 `get_settlement_summary`:** 근거 ID 목록에 새 `M:pg_*` 5개를 추가하고, `platforms[]`에 `lag_days`, `monthly_take_rate[]`에 `fee_rate`·`offset_rate`를 포함한다. `unmatched[]`·`advance` 세부는 여전히 보내지 않는다(건수·비중만).

**결정적 검사(`check_grounding`):** officer_checks마다
- 근거 ID가 1개 이상이고 모두 카탈로그에 있다.
- 정산 계열 근거(`M:pg_`로 시작하거나 `P:R107:`·`P:R108:`로 시작)가 1개 이상이다.
- 문장 속 숫자가 인용 근거 값과 맞는다(`ungrounded`, 기존 허용 오차).
- 3개 초과면 지적. 정산 자료가 없는데(`settlement.available`이 거짓) 항목이 있으면 지적.

**검토자:** 입력에 `officer_checks`(`check_index`, `text`, `evidence`)를 넣는다. 출력 스키마에 `check_verdicts`(`check_index`, `supported`, `reason`)를 추가하고 `required`에 넣는다. 지시문: "확인 사항은 주장이 아니라 확인 권고다. 인용 근거 값이 그 확인이 필요한 이유를 뒷받침하면 supported=true. 승인·거절·금리를 지시하거나 근거와 무관하면 false." `_review_issues`가 `officer_checks[i]` 지적을 claims와 같은 방식으로 만든다.

**라운드 처리:** 확인 사항 지적은 claims 지적과 똑같이 다음 라운드 입력이 되고 최대 3라운드 규칙도 같다(일관성, 평가 지표가 그대로 잰다). `_to_assessment`는 계약 검증에 실패한 항목을 버리고(claims와 같은 방식), 마지막 라운드 검토자의 `check_verdicts`로 각 항목의 `supported`를 채운다(판정 없으면 None). 검토에 실패한 항목도 숨기지 않는다(설계 판단: 심사역이 경고와 함께 본다).

**인용할 수 없는 숫자(설계 판단):** `lag_days`, 월별 `fee_rate`·`offset_rate`는 맥락 정보이고 근거 ID가 없다. 플랫폼별·월별 ID를 새로 만들지 않고, 지시문에 "get_settlement_summary의 플랫폼별 지연 일수·월별 수수료율·상계율 숫자는 문장에 쓰지 말고 M:pg_* 값만 인용한다"를 명시한다(기존 "근거 목록에 없는 숫자 금지" 규칙의 구체화).

**원천 세부 범위(설계 판단):** 2장 반목표의 "원천 세부가 LLM에 가지 않는다"는 이번에 새로 만드는 정산 경로(`unmatched[]`·`advance` 세부)에만 해당한다. 기존 `query_transactions`가 가명처리한 적요(선정산업체 같은 거래 상대방 이름 포함)를 주는 동작은 바꾸지 않는다. 확인 사항 문장은 "선정산" 같은 일반 명사로 쓰라고 지시한다.

### 4.4 오케스트레이터

`assess_credit`가 저장하는 평가 문서(`model_dump`)에 `officer_checks`가 자연히 들어간다. `pg_ledger` 상세 저장 위치(`doc.underwriting.pg_ledger`)도 그대로다. 오케스트레이터 코드 변경은 없을 것으로 본다(빌더 확인).

```
  2. …
```

- KPI 5개: 기존 3개 + 현금화 일수 + 선정산 추정(건수, 비중이 있으면 부제에 표시, 1건 이상이면 빨강).
- "지표 읽는 법"은 `<details>`로 접는다. 문구는 콘솔 상수(코드)로 둔다.
- 플랫폼 비중 표 또는 막대 라벨에 표준 정산 주기(문자열 상수)와 `lag_days`를 함께 보인다.
- 월별 공제율은 수수료·상계를 2색으로 나눠 보인다. 구 문서(`fee_rate` 없음)는 기존 단색 막대로 그린다.
- 미입금 표에 "추정 원인" 열.
- 확인 사항 블록: `assessment.officer_checks`가 있을 때만. 근거 ID는 기존 `opinion.py` 라벨 맵으로 사람이 읽는 이름과 값으로 보인다(새 `M:pg_*` 라벨 추가). 검증 표시는 항목별 `supported`(true ✓ 검토 통과, false "검토 미통과" 경고색, None "검토 결과 없음")이고 제목의 "검토자 검증 n/m"은 true 개수/전체 개수다.
- 새 필드가 없는 옛 문서: 새 KPI는 "—", 확인 사항 블록은 "2026-11-10 이전 심사분은 확인 사항이 없습니다" 안내.

### 4.6 심사 도우미(`src/console/officer_chat.py`)

스냅샷의 `SETTLEMENT_KEYS`에 새 지표 5개를 추가하고, 스냅샷에 `officer_checks`(text와 근거 값)를 넣는다. 미입금 세부·선지급 금액은 넣지 않는다(기존 가명·집계 원칙). 에이전트 지시문 변경은 필요 시 한 줄("정산 확인 사항이 있으면 그 근거로 답한다").

### 4.7 평가(`src/evals/`)

- 심사 suite: ASSIGNED 사례에 `settlement_check_detected`(최종 평가의 officer_checks 중 `M:pg_advance_share`·`M:pg_reconciliation_ratio`·`P:R108`을 인용한 항목이 있음)를 추가하고 config 집계에 `settlement_check_rate`, 실패 유형 `settlement_check_missed`와 리포트 조치 문구를 추가한다.
- `src/evals/fake.py`가 정산 자료가 있으면 확인 사항 1개, 검토자 가짜 출력에 `check_verdicts`를 낸다.
- `ops eval`은 비용이 들어 별도 승인 후 실행한다(이번 범위에서 실행하지 않음).

## 5. 오류 처리

- 분석가가 `officer_checks`를 빠뜨림: strict 스키마라 필수지만 빈 배열은 허용. 정산 자료가 있는데 비어 있어도 실패로 보지 않는다(평가가 비율로 잰다).
- 검토자가 `check_verdicts`를 빠뜨림: 해당 항목은 "검토 결과 없음" 지적(claims와 같음).
- 상수표에 없는 플랫폼: 현금화 일수에서 빼고, 모두 없으면 None.
- 선정산 추정 오탐: 정상 셀러는 미매칭이 거의 없어 후보 자체가 적다. 테스트로 20명 정상 셀러 0건을 고정한다.
