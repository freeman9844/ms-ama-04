# 에이전트와 처음 개발해 본 이야기 — 데일리 블로그 설계

## 1. 의도와 이유

사내 아키텍트 과정의 캡스톤(AMALend, 에이전트 기반 현금흐름 대출 데모)을 2026-10-26부터 2026-11-17까지 Copilot CLI 에이전트와 함께 만들었다. 이 과정의 시행착오를 날짜순 블로그로 남긴다.

- **독자:** AI 코딩 에이전트와 함께 처음 개발해 보는 사람.
- **얻어 갈 것:** "나도 여기서 막히겠구나, 이렇게 넘어가면 되겠구나" 하는 미리 겪는 경험. 기술 튜토리얼이 아니라 경험담이다.
- **중심 줄기:** Copilot 에이전트와 일하는 법을 배워 간 과정(질문·브레인스토밍·계획·서브에이전트 위임·리뷰·재시도·실패 복구). Azure AI Foundry 에이전트를 만든 일은 그 소재로만 쓴다.
- **민감 정보는 모두 지운다.**

## 2. 목표 / 비목표 / 반목표

**목표**
- 10/26~11/17 기록을 하루 한 편 기준(기록이 적은 날은 앞뒤와 묶어) 약 15~18편으로 만든다.
- 각 편을 영문으로 먼저 쓰고, 그다음 한글판을 쓴다. 두 판은 서로 전환 링크로 짝을 이룬다.
- GitHub Pages로 공개한다.

**비목표**
- Azure·Foundry 사용법 튜토리얼, 코드 해설.
- 과제 산출물(docs/) 개편.

**반목표(기술적으로 돌아가도 실패로 보는 것)**
- 민감 정보가 한 건이라도 공개 사이트나 커밋에 남는 것.
- 커밋 목록을 나열한 변경 기록처럼 읽히는 것.
- 실제로 없던 일을 지어내는 것. 추측한 동기는 추측으로 쓰거나 저자 확인을 받는다.
- 에이전트를 과장되게 칭찬하거나 깎아내리는 것. 잘된 일과 어긋난 일을 함께 쓴다.

## 3. 제약

- **위치:** 이 저장소(`freeman9844/ms-ama-04`, 공개) 루트의 `blog/` 폴더. 나중에 별도 저장소로 옮길 수 있게 `blog/` 안에서 완결되게 만든다(사이트 설정·레이아웃·글·검사 스크립트 모두 `blog/` 안, 저장소의 다른 경로를 참조하지 않음. 코드·커밋 링크는 GitHub 절대 URL로).
- **기존 문서 테스트:** `tests/docs/test_docs.py`는 `docs/`만 검사하므로 `blog/`는 영향받지 않는다. 기존 전체 테스트는 계속 통과해야 한다.
- **푸시·Pages 활성화는 저자 승인 후에만 한다.**
- **원자료(세션 대화 원문, 날짜별 자료 묶음)는 커밋하지 않는다.** 원자료에는 민감 정보가 있으므로 세션 작업 폴더(커밋 밖)에만 둔다.
- **언어:** 영문 먼저 작성 → 한글판. 한글판은 저자의 Medium 문체(짧은 인사로 시작, 상황 먼저, "먼저/다음으로/그럼/이제" 같은 연결, 설명 뒤 관찰 결과, 회고로 마무리, 영어 용어는 그대로 섞어 씀). 영문판은 같은 흐름을 영어 블로그 말투로.

## 6.1 빌더 점검 후 내린 결정(저자 확인 대상)
- **다른 시도 저장소는 링크하지 않는다.** 일부는 회사 계정 저장소이거나 원격이 없다. 글에서는 "시도 1~7"처럼 부르고, 폴더 이름·회사 계정 이름은 쓰지 않는다. 링크는 이 공개 저장소(`freeman9844/ms-ama-04`)로만.
- **이미 공개된 식별자도 글에서는 가린다.** 저장소에 이미 있는 리소스 해시·Job ID라도 글 본문에는 자리표시로 쓰고, 그런 경로가 들어간 링크는 걸지 않는다(검사 규칙을 단순하게 유지).
- **문체는 첫 편으로 먼저 확인받는다.** 첫 편(영문+한글)을 완성해 저자 승인을 받은 뒤 나머지를 쓴다.
- **질의응답 세션(26b23252…)은 저자 발언과 에이전트 답만 쓴다.** 제3자의 말이 있으면 쓰지 않는다.
- **익명 처리 검사:** 7.4의 지울 것에 실명(한글·영문), 사용자명, 회사 이름, 회사 계정 이름, 과정 이름을 더한다. 회사 이름처럼 일반 단어인 것은 Azure·Microsoft 제품명(예: "Microsoft Foundry", "Microsoft Entra")과 구분해 회사 소속을 드러내는 표현만 걸러낸다.

## 7. 설계(제안 — 저자 승인 대상)

### 7.1 한 편의 구성
1. 그날 하려던 일(한두 문단, 상황 먼저)
2. 에이전트에게 어떻게 맡겼나(실제 요청을 짧게 인용 — 민감 정보 제거 후)
3. 어긋난 지점(오해·실패·되돌린 일·재시도)
4. 어떻게 넘어갔나
5. 그날의 교훈 한 줄(**Takeaway / 오늘의 교훈**) — 다른 사람이 그대로 가져다 쓸 수 있는 문장

기술 내용은 이야기를 이해하는 데 필요한 만큼만. 분량은 편당 영문 약 800~1,500단어.

### 7.2 날짜 묶기
- 기록(세션 대화 수·커밋 수)이 적은 날은 앞뒤와 한 편으로 묶는다. 후보: 10/29~10/30, 11/05~11/07, 11/12~11/16.
- 최종 편 구성은 날짜별 자료를 모은 뒤 목차(편 제목 + 날짜 범위 + 한 줄 요약)로 저자 승인을 받는다.

### 7.3 사이트
- Jekyll, `blog/` 를 사이트 루트로. GitHub Actions 워크플로(`.github/workflows/blog-pages.yml`)가 `blog/`를 빌드해 Pages로 배포한다(Pages 소스 = GitHub Actions). 워크플로 파일은 저장소 루트 `.github/`에 있어야 하는 GitHub 규칙상 유일한 `blog/` 밖 파일이다.
- 주소: `https://freeman9844.github.io/ms-ama-04/` (`baseurl: /ms-ama-04`).
- 구조: `blog/_posts/en/YYYY-MM-DD-slug.md`, `blog/_posts/ko/YYYY-MM-DD-slug.md`. 앞머리에 `lang`(en/ko)과 짝을 잇는 `ref`(예: `day-01`). 글 위쪽에 `EN | 한국어` 전환 링크.
- 첫 화면: 영문 목록(`/en/`)과 한글 목록(`/ko/`)으로 가는 소개 페이지. 소개에는 프로젝트 한 단락 + 독자에게 하는 말 + 편 목록.
- 테마: GitHub Pages 지원 테마(minima)를 기본으로, 가독성용 최소 CSS만 더한다.

### 7.4 민감 정보 처리
- **지울 것:** 구독·테넌트·객체 ID(GUID), IP 주소, 리소스 이름 해시 접미사(배포 때 붙는 13자 무작위 접미사), 이메일, 사내 계정·테넌트 이름, 로컬 사용자 경로(`C:\Users\…`), 토큰·키 모양 문자열, 과제 채점 기준(rubric) 원문.
- **바꿔 쓰는 방식:** 이야기에 필요하면 `<subscription-id>`, `<my-ip>`, `func-<hash>` 처럼 자리표시로.
- **자동 검사:** `blog/tools/scan_sensitive.py`가 `blog/` 아래 모든 글을 정규식으로 검사하고, 걸리면 실패한다. 검사 대상 패턴에는 실제 값 목록(해시 접미사, 사용자명 등)도 포함하되, 그 실제 값 목록 파일은 커밋하지 않고 로컬 환경변수/세션 폴더로만 준다. 커밋되는 검사기는 일반 패턴(GUID·IPv4·이메일·`C:\Users`·키 모양)만 가진다.
- Pages 워크플로에서도 일반 패턴 검사를 빌드 전에 돌려, 걸리면 배포하지 않는다.
- 공개 전 저자 검토를 한 번 받는다.

### 7.5 작업 흐름
1. 날짜별 자료 묶음 생성(스크립트, 세션 작업 폴더에만 저장): 날짜마다 세션 대화 요약·저자 메시지·커밋 제목·배포 이력 항목.
2. 목차(편 구성) 저자 승인.
3. 첫 편 영문 → 한글판 → 문체 저자 승인. 이후 편마다 영문 초안 → 한글판.
4. 민감 정보 자동 검사 + 저자 검토.
5. 저자 승인 후 커밋·푸시, Pages 활성화.
