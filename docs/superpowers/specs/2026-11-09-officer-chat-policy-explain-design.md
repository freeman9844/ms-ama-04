# 심사 도우미 정책 판정 설명 설계

## 목적

심사역 결정 채팅(심사 도우미)이 "금리 구간 A는 무엇인가", "한도가 왜 500만 원인가", "R102는 왜 안 걸렸나" 같은 정책 판정 질문에 답하게 한다. 지금 스냅샷에는 판정·규정 버전·한도·구간 문자·걸린 사유 코드만 있어서, 규정 내용이나 이 건에 대한 계산 과정을 물으면 "자료에 없음"이 된다(2026-11-09 라이브에서 "금리 구간 A" 질문으로 확인).

## 목표·비목표

- **목표:** 신청 건에 적용된 규정 버전의 원문(상품 한도, 부적격·회부 규칙, 금리 구간표)과 이 건의 계산 과정(한도 산식, 구간 결정, 모든 규칙의 실제값·기준값·결과)을 스냅샷에 넣어 채팅이 출처를 밝혀 답하게 한다.
- **목표:** 계산 과정은 정책 엔진과 같은 코드로 만든다. LLM이 계산하지 않는다.
- **비목표:** 구간별 실제 금리, 기준값을 정한 이유. 이 정보는 정책에 정의돼 있지 않으며 상품 결정이 필요하다. 채팅은 계속 "자료에 없음"으로 답한다.
- **비목표:** 판정을 바꾸거나 다시 내리는 것. 저장된 판정이 권위다.
- **반목표:** 재계산한 결과가 저장된 판정과 다른데도 계산 과정을 보여 주는 것. 이 경우 심사역에게 틀린 근거를 준다.

## 방식(검토한 대안)

| 방식 | 내용 | 득실 |
|---|---|---|
| **A. 콘솔이 규정 파일·엔진 코드를 같이 담기 (선택)** | 콘솔 이미지에 `policy` 패키지의 순수 코드(`rules.py`·`engine.py`)와 `rulesets/*.yaml`을 복사하고, 채팅 때 `rules_version`으로 규정을 읽어 계산 과정을 다시 만든다 | 이미 처리된 신청에도 바로 동작하고 콘솔만 배포하면 된다. 대신 "콘솔은 정책 패키지를 가져오지 않는다"는 분리가 약해진다 |
| B. 판정 시 설명을 문서에 저장 | 정책 엔진이 설명을 함께 반환하고 오케스트레이터가 신청 문서에 저장한다 | 감사 기록으로는 가장 정확하다. 계약·오케스트레이터·정책 서비스를 모두 다시 배포해야 하고 이전 신청은 답할 수 없다 |
| C. 채팅 때 정책 서비스 API 호출 | 새 `explain` API를 콘솔이 호출한다 | 네트워크 경로와 인프라가 늘어나고 정책 서비스 장애가 채팅으로 번진다 |

사용자가 A를 골랐다(2026-11-09).

## 설계

1. **엔진(`src/policy/engine.py`):** `explain(features, rules)`을 추가한다. 규칙마다 실제값·기준값·결과(`hit`/`pass`/`not_applied`, 값이 없으면 `not_applied`)를 내고, 한도 산식(신청액, 월평균 입금×배수, 상품 최대, 내림 전 값, 단위, 결과)과 구간 결정(DSCR, 구간표, 선택된 구간)도 낸다. R900·R901(엔진이 만드는 사유)도 같은 형식으로 포함한다. `evaluate()`는 `explain()`의 결과로 `PolicyDecision`을 만들어, 판정과 설명이 한 코드 경로를 쓴다. 기존 `evaluate()`의 결과는 그대로여야 한다(기존 정책 테스트가 그대로 통과해야 함).
2. **규정 조회(`src/policy/rules.py`):** `rulesets/` 안의 YAML을 읽어 `version` → `RuleSet`을 돌려주는 함수(예: `rules_for_version(version)`)를 추가한다. 모르는 버전이면 `None`을 돌려준다.
3. **스냅샷(`src/console/officer_chat.py`):** `policy` 아래에 두 키를 더한다.
   - `rules`: 적용 버전의 상품 한도·배수·단위, 부적격·회부 규칙(코드·메시지·지표·연산·기준값), 금리 구간표. 버전을 모르면 `null`.
   - `trace`: 위 `explain()` 결과. 신청 문서의 `underwriting.features`를 `CashFlowFeatures`로 검증해 계산한다. 다음 경우에는 `trace`를 `null`로 두고 `trace_note`에 이유를 짧게 적는다: 규정 버전을 모름, 특성 검증 실패, 재계산한 판정·한도·구간·사유 코드 집합이 저장된 판정과 다름.
   - `cashflow.capacity`에 월 상환액 계산에 쓴 가정 금리(`agents.features.ANNUAL_RATE`, 연 8%)를 `assumed_annual_rate`로 넣는다.
   - 스냅샷 줄이기(`_fit`)는 `policy`를 줄이지 않는다. 추가분은 약 2~3KB로 24KB 상한 안이다.
4. **지시문(`src/agents/officer_chat.py`):** 출처 표기 두 가지를 더한다. 규정 원문은 "(정책 규정 <버전>)", 이 건의 계산은 "(정책 계산)". 구간별 실제 금리는 자료에 없다고 답하고, 월 상환액은 가정 금리 기준이라는 점을 밝힌다. `trace`가 `null`이면 `trace_note`를 알리고 계산 과정은 추측하지 않는다.
5. **콘솔 이미지(`src/console/Dockerfile`, `requirements-console.txt`):** `src/policy/__init__.py`, `rules.py`, `engine.py`, `rulesets/`를 `/app/policy`로 복사한다(`app.py`·`main.py`는 복사하지 않음). `PyYAML==6.0.3`을 추가한다(`requirements-api.txt`와 같은 버전).
6. **문서:** `docs/agents.md` 심사역 결정 채팅 절의 스냅샷 설명, `src/console/assessment.py` 모듈 설명의 "정책 패키지를 가져오지 않는다" 문장(이제 채팅용으로 가져온다는 사실을 반영), 배포 기록.

## 제약

- 가명화 원칙은 그대로다. 규정과 계산 과정에는 실명·식별자가 없다(신청 ID만 있음).
- 콘솔에서 정책 엔진 코드는 설명용으로만 쓴다. 판정을 저장하거나 바꾸지 않는다.
- 기존 정책 엔진 동작과 `/v1/decisions` 응답은 바뀌지 않는다.

## 검증

- 단위 테스트: `explain()`이 규칙별 결과·한도 산식·구간 결정을 맞게 내는지, 그리고 `evaluate()`와 판정이 일치하는지(v1·v2·v3 규정, 부적격·회부·적격 각 한 건씩). 스냅샷의 `rules`/`trace` 생성, 버전 모름·검증 실패·불일치 때 `trace=null`.
- 이미지 테스트: 콘솔 Dockerfile이 `policy` 순수 모듈과 `rulesets`를 복사하고 `app.py`/`main.py`는 복사하지 않는지.
- 라이브: 콘솔 배포 후 실제 신청에서 "금리 구간 A(또는 해당 구간)의 기준은?", "한도는 어떻게 계산됐나?", "R102는 왜 안 걸렸나?", "구간별 금리는?" 네 질문. 앞의 세 질문은 출처를 표기하고 수치가 규정과 맞아야 하며, 마지막 질문은 "자료에 없음"이어야 한다.

## 빌더에게 맡기는 것

- `explain()`의 반환 타입(데이터클래스 또는 pydantic 모델)과 필드 이름.
- `rules_for_version`의 캐시 방식.
