# 데모 대비책 (fallback)

데모 전 점검, 라이브가 늦거나 실패할 때의 전환 대사, 전체 장애 때 녹화본으로 넘어가는 절차입니다. 장면별 대본은 [demo-script](demo-script.md), 리허설 기록은 [rehearsal](rehearsal.md)에 있습니다.

> **합성 데이터 기준.** 이 문서의 수치는 합성 데이터 기준이며 모두 기존 실측 산출물에서 인용하고 출처 경로를 옆에 적었습니다. 사전 건의 ID와 확인 시각은 2026-11-03 리허설에서 채웠습니다.

## 사전 준비 목록

데모 전날까지 콘솔에서 만들어 둡니다. 동의 유효 기간은 90일이라(`src/orchestrator/journey/models.py`의 `CONSENT_TTL_DAYS`) 그보다 오래된 사전 건은 다시 만듭니다. 아래 ID는 2026-11-03에 준비한 건이므로 그날부터 90일이 지나기 전에 다시 만듭니다. 세 건 모두 `demo-healthy-001`로 만듭니다. 아래 ID는 P8(온라인 셀러 소액 대출 데이터) 이전 데이터와 옛 신청인 ID(`demo-cafe-001`)로 만든 기록이므로, P8을 Azure에 배포한 뒤 다시 만들고 ID를 바꿉니다.

| 이름 | 만드는 방법 | ID(2026-11-03 준비) | 확인 방법 |
|---|---|---|---|
| A 승인 신청 | `새 신청`으로 `demo-healthy-001`을 제출하고 `심사역 대기`가 되면 `승인`·`결정 보내기`. | 신청 ID: `app-20261103-a30edc` (상태 `승인`). 이 건의 사후 재생은 쓰지 않고 신청 상세만 씁니다. | `/applications/<신청 ID>`의 상태가 `승인`이고 `타임라인`·`주장과 근거`·`심사역 결정`이 보임 |

## 시작 전 점검

시작 5~10분 전에 순서대로 확인합니다. 명령은 [operate](../runbook/operate.md)·[deploy](../runbook/deploy.md)의 형태 그대로입니다.

- [ ] `python -m ops resume` 완료. Service Bus를 지워 둔 상태였다면 복구에 몇 분 걸립니다(실측 4.5~4.7분, `docs/runbook/operate.md`). 이미 있으면 그대로 둡니다.
- [ ] `python -m ops smoke` 통과. VNet 안 점검 항목과 콘솔 로그인 관문을 함께 확인합니다([operate](../runbook/operate.md#smoke)).
- [ ] 콘솔 접속. 주소는 `azd env get-values`의 `CONSOLE_URL`입니다. 접속이 403이면 운영자 공인 IP가 console ingress 허용 목록과 달라진 것입니다(`python -m ops window status`로 확인). 이때는 `operator-alt` 규칙으로 현재 IP를 임시 허용하고 데모 뒤 지웁니다 — [deploy](../runbook/deploy.md#운영자-ip가-바뀔-때)의 절차를 그대로 따릅니다. 회사 NAT처럼 출구 IP가 여러 개로 돌면 403이 반복될 수 있으니, 바뀔 때마다 같은 절차로 `/32` 임시 규칙(`operator-alt2`, `operator-alt3` …)을 하나씩 추가합니다.
- [ ] 라이브 신청 ID를 메모할 곳(종이·메모장)을 준비합니다.
- [ ] `python -m ops fault status`가 `source: off`, `policy: off`로 둘 다 꺼져 있음. 켜져 있으면 `python -m ops fault source off` / `python -m ops fault policy off`로 끕니다(`source`가 `flaky`이면 사후 재생이 실패합니다).
- [ ] 사전 건 A·B·C의 확인 방법(위 표)을 한 번씩 통과.
- [ ] 브라우저 탭 순서 맞추기: 1 콘솔 목록(`/`), 2 사전 건 A, 3 사전 대출 B, 4 사전 동의 C 증명.
- [ ] 녹화본 파일을 발표 PC에서 바로 재생할 수 있는지 확인.

## 라이브 지연·실패 시

말을 멈추지 않고 아래 대사로 이어 갑니다. 전환 기준 시간은 [demo-script](demo-script.md)의 장면별 "전환 지점"과 같습니다(계획값, 리허설에서 조정).

| 장면 | 상황 | 전환 대사 | 동작 |
|---|---|---|---|
| 0:15 신청과 실시간 진행 | 0:50에 라이브 건 상태가 `심사역 대기`가 아님(리허설 실측 62초라 대개 해당) | "라이브 건은 뒤에서 계속 돌고 있습니다. 같은 단계까지 끝낸 건을 보겠습니다." | 탭 2(사전 건 A)로 이동. 1:45 장면은 라이브 건의 동의를 그대로 만료합니다(승인 전이어도 됩니다). |
| 0:50 심사 근거와 승인 | 승인 폼 오류가 풀리지 않거나 10초 안에 상태가 `승인`이 안 됨 | "승인 결정은 큐를 거쳐 반영됩니다. 이미 승인까지 끝난 건에서 근거를 보겠습니다." | 탭 2(사전 건 A)의 `주장과 근거`·`심사역 결정`을 보여 줌. 1:45 장면은 라이브 건의 동의를 그대로 만료(승인 여부 무관). |
| 1:20 조기경보 | `/loans/<대출 ID>`가 안 열리거나 `재생 실패` | "13주 재생은 시간이 걸려 미리 돌려 둔 결과입니다." | 사전 대출 B를 새로 고침. 계속 안 되면 말로만 설명하고(경보가 연체일보다 67일 앞선 실측, `docs/runbook/deploy-history.md:344`) 다음 장면으로. |
| 1:45 동의 만료 | 라이브 건 동의 행에 `지금 만료(데모)` 버튼이 없음, 또는 `지금 만료(데모)` 뒤 15초 안에 `삭제 증명` 링크가 안 생기거나 `미완료` | "삭제는 항목마다 검증하고, 검증이 안 되면 재시도합니다. 이미 완료된 증명을 보겠습니다." | 탭 4(사전 동의 C)의 삭제 증명을 보여 줌. |

공통 규칙:

- 라이브 건의 동의를 만료시킨 뒤에는 그 건의 사후 재생을 시작할 수 없으므로 사전 대출 B에서는 절대 `지금 만료(데모)`를 누르지 않습니다.
- 사전 건 A·C를 쓴 뒤에도 라이브 건은 계속 진행되므로, 시간이 남으면 마지막에 목록으로 돌아가 상태를 보여 줍니다.
- 차주 화면(`/borrower`)의 `동의 철회`를 쓰지 않습니다(신청이 `철회 종료`로 끝납니다). 1:45 장면은 `지금 만료(데모)`입니다.
- 목록의 다른 `심사역 대기` 건(사전 건 C의 신청 등)을 승인하지 않습니다. 승인은 메모한 라이브 신청 ID에만 합니다.

## 전체 장애 시

콘솔 접속 불가, 큐·함수 전체 장애, 네트워크 장애로 사전 건도 열 수 없을 때입니다.

- **녹화본:** 리허설 때 발표자가 직접 대본대로 화면을 녹화합니다. 녹화본은 저장소에 넣지 않고 발표 PC에 보관합니다. 개인정보가 없는 합성 데이터 화면만 담습니다.
- **판단 기준:** 시작 전 점검이 통과하지 않거나, 0:15 장면에서 콘솔이 열리지 않으면 바로 녹화본으로 넘어갑니다. 도중에 장애가 나면 현재 장면을 끝내지 않고 넘어갑니다.
- **전환 대사:** "지금 환경에 일시적인 문제가 있어, 같은 순서로 미리 녹화한 화면으로 보겠습니다. 화면은 오늘 데모와 같은 콘솔입니다."
- **절차:** 1) 녹화본을 전체 화면으로 재생하고, 2) 재생 시점에 맞춰 [demo-script](demo-script.md)의 "말"을 그대로 읽고, 3) 데모가 끝나면 원인을 짧게 말한 뒤 질문으로 넘어갑니다. 장애 원인 확인은 데모 뒤에 [troubleshooting](../runbook/troubleshooting.md)으로 합니다.
